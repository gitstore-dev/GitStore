# Research: Controller Watch API and Status Subresource Contract

## R1: Watch transport mechanism

**Decision**: Use gqlgen's existing GraphQL `Subscription` type over the already-wired WebSocket transport. Add `watchCategories(namespace: String, selector: LabelSelector, resourceVersion: String): WatchEvent!` to `shared/schemas/category.graphqls` (the per-kind entry point for the one core kind implemented now) and `watchResources(kind: String!, namespace: String, selector: LabelSelector, resourceVersion: String): WatchEvent!` to `shared/schemas/schema.graphqls` (the generic CRD entry point), matching the user's own proposal.

**Rationale**: `gitstore-api/internal/app/server.go` already imports `github.com/99designs/gqlgen/graphql/handler/transport` and calls `gqlServer.AddTransport(transport.Websocket{...})` — the transport is live and unused; no new dependency, no new port, no new protocol. gqlgen resolves a `Subscription` root field to a Go channel (`<-chan *T`) the generated code drains and streams to the client, which maps directly onto the existing `internal/listwatch.Watcher[T].Events() <-chan WatchEvent[T]` shape the controller-manager already expects. This was explicitly the deferred decision from spec 036's research: *"the concrete GraphQL-subscription-backed implementation is deferred to whichever spec first needs a real T... e.g. issue #244."*

**Alternatives considered**:
- *Dedicated gRPC streaming endpoint* (mirroring `gitstore-git-service`'s notification stream from issue #139): rejected because #139 is itself unimplemented (OPEN), and building a second streaming transport in a different protocol duplicates work the WebSocket transport already does for free. Revisit only if GraphQL subscriptions prove operationally unworkable at scale — out of scope for that risk at current scale (constitution: 1-5 concurrent admin users, single-instance deployment).
- *Long-polling GraphQL query* (`categoriesSince(resourceVersion): [Category!]!`): rejected because it reintroduces the polling behaviour spec 036 and this spec are explicitly designed to avoid, and doesn't naturally model a persistent "subscribe once, receive forever" cursor session the way `Subscription` does.

## R2: Change-event production (server-side "what triggers a WatchEvent")

**Decision**: Introduce a small in-process event bus (`gitstore-api/internal/eventbus`) that `AdmitResources` (in `cataloggrpc/server.go`) publishes to synchronously after each successful create/update/delete of a `CategoryTaxonomy` row, and that the `watchCategories`/`watchResources` subscription resolvers subscribe to for the lifetime of a client's WebSocket connection.

**Rationale**: `AdmitResources` already knows the outcome of every admission (`admitCategoryTaxonomyWithContext` returns the resulting resource and its new `resourceVersion` via `nextResourceVersion`) and already runs in-process in the same `gitstore-api` binary as the GraphQL server — no cross-service call is needed to observe the change. This matches the constitution's Simplicity principle (in-memory preferred over external dependencies) and the existing single-instance deployment assumption; a durable/distributed event log (Kafka, Redis Streams) would be premature given the constitution's explicit "in-memory caching preferred over external dependencies" guidance and the current 1-5 concurrent user scale.

**Alternatives considered**:
- *Polling the datastore for a `resource_version > cursor` diff on each subscriber tick*: rejected — reintroduces polling internally even if the client-facing API is a subscription, and doesn't naturally support many concurrent watchers without redundant datastore scans.
- *A durable outbox table replayed by subscribers*: rejected as premature — durability is only needed to survive a `gitstore-api` process restart while a watch is open, and the existing list-then-watch contract already handles that case at the controller-manager layer (`Runner[T].bootstrapOrResume` re-lists on any watch-stream error, treating a `gitstore-api` restart as an ordinary reconnect-and-relist rather than requiring the event source itself to be durable). If cross-restart *event replay* (not just resource replay) is later needed, that is exactly the scope of the still-open issue #139 (git-service → API gRPC event stream) and issue #131's own "compacted event log" language — this spec's in-memory bus satisfies the *current* Watcher[T] contract because ErrWatchExpired already covers the "I can't replay that far back" case.

## R3: `resourceVersion` semantics and the "expired cursor" signal

**Decision**: Reuse the existing numeric-string `resourceVersion` already written by `nextResourceVersion` (`gitstore-api/internal/cataloggrpc/server.go:702`) as the watch cursor — no new versioning scheme. The event bus retains a bounded in-memory ring buffer of the last N published events per kind (N configurable, default large enough to cover the `CheckpointFlushIntervalEvents` default of 100 plus headroom). A `Watch(ctx, resourceVersion)` call whose requested cursor is older than the oldest event still in the ring buffer returns a `WatchEvent` (or subscription error) that the controller-manager's existing `listwatch.ErrWatchExpired` check already knows how to handle.

**Rationale**: The controller-manager side (`internal/listwatch/types.go`, `internal/listwatch/runner.go`) is already fully built and tested against exactly this contract from spec 036 — `ErrWatchExpired` triggers `recoverFromExpiry` (re-list + fresh checkpoint). This spec only needs to make the *server* honour that contract; no new client-side logic is needed. Reusing the existing numeric `resource_version` column (already present on `CategoryTaxonomy` and incremented on every write) avoids a schema migration.

**Alternatives considered**:
- *Vector-clock or Lamport-timestamp cursor*: rejected — massive over-engineering for a single-writer, single-instance `gitstore-api`; the existing per-row incrementing counter is already suffice and the client (`Runner[T]`) treats the cursor as an opaque token per spec 036's own Assumptions ("ResourceVersion is opaque and compared only for equality, never ordered").
- *Unbounded event retention (never expire)*: rejected — unbounded memory growth in a long-running process; the spec explicitly requires an expired-cursor signal to exist (FR-004), so *some* bound is required by definition.

## R4: Status-update mutation shape and partial-merge semantics

**Decision**: Add `updateCategoryStatus(input: UpdateCategoryStatusInput!): UpdateCategoryStatusPayload!` to `shared/schemas/category.graphqls`, where the input carries `name`, `namespace`, `resourceVersion` (required precondition), and optional `observedGeneration`, `lastAppliedRevision`, `conditions`, `resolved` — mirroring the `StatusPatch` struct contract already defined in `specs/026-reconcile-handler/contracts/status-patch-api.md` and already implemented client-side as `gitstore-controller-manager/internal/status.StatusPatch`/`StatusClient`. Only fields present in the input are changed; the resolver reads the current row, applies non-nil fields, writes back through `store.UpdateCategoryTaxonomy`, and increments `resourceVersion` exactly once per successful call.

**Rationale**: The client-side contract (`internal/status.StatusClient.Apply(ctx, key, patch) error`, `internal/status.StatusPatch`) is already fully implemented and unit-tested in the controller-manager (spec 026) — this spec only needs to provide the GraphQL mutation that a concrete `StatusClient` implementation calls. Naming follows the existing `create<Kind>`/`update<Kind>`/`delete<Kind>` convention already used for `Category` (`updateCategory`) rather than inventing a `patch<Kind>Status` verb, since "update" already means "partial-merge, not full-replace" elsewhere in this codebase (see `UpdateCategoryInput` in `category.graphqls`, which also only carries a subset of mutable fields).

**Alternatives considered**:
- *`patchCategoryStatus` naming*: considered per the user's own alternate proposal, but rejected in favour of consistency with the existing `updateCategory` naming already in the schema — introducing a second verb (`patch` vs `update`) for the same "partial merge" semantic elsewhere in the same schema would be a naming inconsistency, not a clarity gain.
- *A single generic `updateResourceStatus(kind: String!, ...)` mutation for all kinds (mirroring `watchResources`)*: rejected for the *initial* status-write path — unlike watch (where a generic kind-parameterised query is cheap because the resolver just re-dispatches to the same event bus), a generic status mutation would need to type-erase the kind-specific `resolved` sub-field (`ResolvedCategoryTaxonomy` for `CategoryTaxonomy`, `ResolvedProductDefinition` for `Product`, etc.), which either requires a JSON-blob `resolved` argument (losing GraphQL's type safety for the one field controllers care about most) or a union/interface type gqlgen does not cleanly support for input types. Per-kind status mutations for core kinds, plus a JSON-blob-based generic mutation reserved specifically for CRD kinds (which have no compile-time-known `resolved` shape anyway), is the pattern used elsewhere in this spec (compare: per-kind `watchCategories` vs. generic `watchResources` — the generic path is reserved for the case, CRDs, where there is no static type to lose).

## R5: Authorization for controller-level status writes

**Decision**: Extend the existing `internal/middleware/security/graphql.go` `GraphQLFieldAuthorizer` switch with a case for `updateCategoryStatus` (and the future generic `updateResourceStatus`) that calls `authz.Authorize(ctx, principal, "category.status.write", auth.ResourceContext{Kind: "categoryTaxonomy", Name: input.Name})`. The controller-manager authenticates as an ordinary bearer-JWT principal (issued via the existing `staticadmin.IssueSession`/`gitctl` tooling) whose roles are bound to a policy granting `category.status.write` (and, generically, `*.status.write`) in `policy.yaml` under `rbac-local`.

**Rationale**: The existing `AuthZProvider.Authorize(ctx, principal, action, resource)` interface already supports exactly this shape of check — `GraphQLFieldAuthorizer` already does per-field, per-argument authorisation for `createNamespace`/`deleteNamespace` using the identical pattern (extract argument via `nestedStringArg`, call `Authorize` with a dot-notation action string, deny on `OutcomeDeny`). No new authorization primitive, no new provider, no new identity mechanism is needed — only a new action string and a new `switch` case, plus a `role_bindings`/`roles` entry in the deployment's `policy.yaml` for a `controller` role. This directly satisfies FR-011's requirement that status writes are "authorise[d]... separately from ordinary read/write access."

**Alternatives considered**:
- *A dedicated machine-to-machine auth provider (mTLS or a new HMAC scheme) specifically for controllers*, mirroring the git-service↔API HMAC interceptor (`gitclient/auth.go`): rejected as unnecessary — that HMAC scheme exists for a gRPC channel with no HTTP-header-based identity concept; GraphQL callers already carry a `Principal` via the existing bearer-JWT authn chain, and `rbac-local` already supports arbitrary role-to-action bindings without code changes. Introducing a second machine-identity mechanism would violate Simplicity/YAGNI without a demonstrated need.
- *Hard-coding "any authenticated principal may write status"* (skip a distinct action check): rejected — this fails FR-011 outright (which requires controller-level authorisation *distinct from* ordinary access) and fails the edge case in User Story 2 AC5 (unauthorised caller must be rejected independent of `resourceVersion`).

## R6: `.spec`/`.metadata` write-rejection enforcement point

**Decision**: Enforce spec-immutability structurally, not via a runtime check: `UpdateCategoryStatusInput` is a GraphQL input type that has no `spec` or author-controlled `metadata` fields at all — it is impossible to submit a spec change through this mutation because the schema does not accept one. The resolver additionally only ever calls a new datastore method (`UpdateCategoryTaxonomyStatus`, distinct from the existing full-object `UpdateCategoryTaxonomy`) that writes exclusively to the `status` column/field, as an additional defence-in-depth layer against a future resolver bug that might otherwise pass an unvalidated struct through.

**Rationale**: A schema that cannot express the forbidden request is strictly stronger than a schema that accepts it and then validates it away — this eliminates an entire class of "did the validator get bypassed" bugs and satisfies FR-010 by construction rather than by runtime check. This mirrors how `ProductStatus`/`CategoryTaxonomyStatus` are already separate Go types (`gitstore-api/internal/catalog/status.go`) from `ProductSpec`/`CategoryTaxonomySpec` — the type system already enforces this separation for reads; this decision extends the same separation to writes.

**Alternatives considered**:
- *A single `updateCategory` mutation accepting an optional `status` block alongside `spec`, with a runtime "reject if status writer lacks spec-write permission" check*: rejected — this is exactly the design FR-010 is written to prevent (a request that CAN attempt to alter spec, gated only by a runtime check that could have a bug), and it conflates two different callers (git-push-driven admission vs. controller status writeback) into one mutation with different permission models, which is the worse design axis per the constitution's Clear Contracts principle.

## R7: Generic CRD-kind support for both watch and status write

**Decision**: `watchResources(kind: String!, ...)` and status writes for CRD kinds return/accept a loosely-typed `WatchEvent`/status shape (JSON-encoded `resolved`/object payload) rather than a generated-per-kind GraphQL type, since a CRD's shape is not known at gqlgen-codegen time. This mirrors the existing `JSON` scalar already used for `ProductObjectMeta.labels`/`annotations` in the schema. Concretely: `type WatchEvent { type: WatchEventType!, kind: String!, namespace: String, name: String, resourceVersion: String!, object: JSON }`.

**Rationale**: gqlgen generates Go types from the schema at build time; a truly generic "any resource" GraphQL type cannot carry compile-time-typed fields for kinds that don't exist in the schema yet (this is precisely why issue #148's "Query Handler Chain of Responsibility" and issue #140's "Universal ScyllaDB Resource Table" initiatives exist as separate, larger efforts — CRD-shape genericity at the datastore layer is out of scope here). Using `JSON` for the payload is consistent with how the schema already handles kind-agnostic data (`ProductObjectMeta.labels: JSON`) and satisfies FR-006/SC-005 (works for a new CRD kind without a schema change) without requiring this spec to solve the much larger "universal resource table" problem.

**Alternatives considered**:
- *Defer CRD support entirely to a future spec, ship only the per-kind `watchCategoryies`/`updateCategoryStatus` now*: rejected — the spec's own FR-006 and SC-005 explicitly require the generic mechanism to exist and be validated by integration tests now, precisely so the *shape* of the generic contract is proven before more core kinds or real CRDs are onboarded (avoiding a redesign later, per FR-006's "without requiring a schema change per new CRD kind"). The generic path can be a thin, JSON-boxed sibling implemented alongside the per-kind path at low incremental cost, rather than a separate large effort.

## R8: Threading kind-specific `resolved` data through the existing generic `StatusClient` interface

**Decision**: Extend the existing `gitstore-controller-manager/internal/status.StatusPatch` struct with one additional field: `Resolved json.RawMessage` (nil = unchanged, matching the existing pointer-field convention for the other optional fields). `StatusClient.Apply(ctx, key, patch *StatusPatch) error` keeps its existing signature — no interface change. A `CategoryTaxonomy` reconciler builds `patch.Resolved` by marshalling its own `ResolvedCategoryTaxonomy`-shaped struct to JSON before calling `Apply`; the `graphqlStatusClient` implementation unmarshals it into the `resolved: ResolvedCategoryTaxonomyInput` GraphQL argument (or passes it as a raw `JSON` scalar for CRD kinds with no static input type).

**Rationale**: Spec 026's own status-patch contract explicitly states "`resolved` is NOT part of the generic patch — it is kind-specific" but does not say how a kind-specific value should reach the wire — that decision was correctly deferred to "whichever spec first needs a real kind" (this spec, per the same pattern as R1/R2). Adding one `json.RawMessage` field to the existing struct (rather than changing the `Apply` method signature, or introducing a second per-kind interface) preserves every existing caller of `StatusClient` (there are none yet with concrete implementations, but the interface itself, used generically across all future reconcilers, stays a single method) while giving each kind an escape hatch for its own resolved shape. `json.RawMessage` (not `any`) is chosen so the controller-manager package continues to have zero compile-time dependency on any particular kind's resolved struct — it only ever passes bytes through.

**Alternatives considered**:
- *Generic `Resolved any` field, type-switched at the `graphqlStatusClient` layer*: rejected — `any` reintroduces a runtime type-assertion failure mode (wrong type passed for a given kind) that `json.RawMessage` avoids entirely, since the reconciler itself is responsible for marshalling its own known type.
- *A second, kind-specific interface (e.g. `CategoryStatusClient` with an `ApplyWithResolved` method) layered on top of `StatusClient`*: rejected — multiplies the number of interfaces reconciler authors need to learn per kind, contradicting the whole point of spec 026 defining one shared `Reconciler`/`StatusClient` contract for "core and CRD kinds" alike.
