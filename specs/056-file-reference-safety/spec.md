# Feature Specification: File Reference Resolution and Deletion Safety

**Feature Branch**: `056-file-reference-safety`

**Created**: 2026-08-20

**Status**: Draft

**Input**: User description: "File Reference Resolution and Deletion Safety (GH#378). Once the File resource exists (GH#79, spec 051), define how deletion of a File affects the resources that reference it via spec.media[*].fileRef (Product, ProductVariant, CategoryTaxonomy, Collection), and build the reverse-reference index this needs using the same metadata.ownerReferences + blockOwnerDeletion mechanism adopted for CategoryTaxonomy (#243, spec 052) — rather than a bespoke fileRef-scan or a new indexing mechanism. Resolve the block-vs-decouple design question for File deletion explicitly, define the reverse-reference index query, and cover both with integration tests."

**Related**: GH#378 (this issue), GH#79/spec 051 (File resource contract — schema only), GH#243/spec 052 (CategoryTaxonomy deletion semantics — ownerReferences/blockOwnerDeletion precedent), `docs/implementation/034-file-media-lifecycle-architecture.md` (reverse-reference index and File Controller design)

## Clarifications

### Session 2026-08-20

- Q: GH#378's Background section leans toward "decouple" for File deletion (media is presentation/degraded-gracefully) but explicitly asks this spec to make and justify the actual call rather than just repeat the lean. Does File deletion block on referencing resources (like CategoryTaxonomy blocks on child categories, spec 052) or decouple (like CategoryTaxonomy decouples from assigned products, spec 052)? → A: Decouple, uniformly, for every consumer kind (`Product`, `ProductVariant`, `CategoryTaxonomy`, `Collection`) and regardless of whether the specific `fileRef` entry is required (`optional: false`) or optional (`optional: true`). Justification, applying spec 052's own test ("block only where no safe default exists"): a missing or removed media reference is already a normal, non-corrupting, recoverable state in this catalog — a broken-image placeholder, not a structural break — unlike a `CategoryTaxonomy` child left pointing at a parent name that resolves to nothing, which breaks the `ancestorPath`/depth invariant spec 039's reconciler maintains. There is no File-side analogue to that invariant: `docs/implementation/034-file-media-lifecycle-architecture.md` §10 already defines a well-formed `False` state for a required `fileRef` (`FileRefConfirmed=False`) and a well-formed silent-omission state for an optional one, exactly parallel to how `CategoryTaxonomy`'s own `spec.parentRef` already has a well-defined `False` state (`ParentResolved=False/ParentNotFound`) without needing blocking. A safe default exists in both the required and optional case; only the downstream severity (whether it gates the dependent's own `Ready`) differs, never whether the deletion is permitted. This decision supersedes the older, blocking `deleteFile` sketch in `docs/implementation/034-file-media-lifecycle-architecture.md` §7c ("Check reverse-reference index → reject with FailedPrecondition if any references exist"), which pre-dates this issue's explicit design question and was drafted before that same document's own §10 required/optional severity vocabulary was reconciled against it. That sketch's *dependent-blocking* step is superseded by this spec; File's own internal finalizer/cleanup-before-hard-delete mechanics for its own processing state are unrelated to dependents and remain File-CRUD scope (out of scope here).
- Q: Does `optional: false` ("required") on a `fileRef` change the answer above — should a required reference make its target File undeletable? → A: No. In the vocabulary this codebase already documents (`docs/implementation/034-file-media-lifecycle-architecture.md` §10's `Ready` composition rule: "`Ready=False` only when a required `fileRef`'s `FileRefConfirmed=False`... a required ref in `Unknown` state keeps the dependent's own `Ready` in `Unknown`, never optimistically `True`"), "required" has always meant "this reference gates the dependent's own `Ready`," not "the referenced File may never be deleted." Reusing that existing meaning is what keeps this decision consistent with the codebase rather than inventing a second, competing meaning for "required." Uniform decouple-always is therefore the correct answer, not merely the simpler one.
- Q: What mechanism identifies which resources reference a given File, so File deletion (and the future File Controller) can act on exactly those resources without a full-table scan? → A: The same `metadata.ownerReferences` + `blockOwnerDeletion` mechanism spec 052 establishes for `CategoryTaxonomy` (per this issue's own title and ask), not a bespoke `(namespace, File.name)` reverse-index table as originally sketched in `docs/implementation/034-file-media-lifecycle-architecture.md` §9, and not a `spec.media[*].fileRef` name-scan. Every resource writes a `{kind: File, name, uid, blockOwnerDeletion: false}` entry once its reference to that File resolves; the reverse-reference index becomes "every resource whose `ownerReferences` names File `uid` X," an indexed lookup on a mechanism this codebase already needs for `CategoryTaxonomy` (spec 052) and can reuse rather than build twice. `blockOwnerDeletion` is uniformly `false` here (never `true`) because nothing about File deletion blocks, per the decision above — this differs from spec 052, where `blockOwnerDeletion` varies (`true` for children, `false` for products) because CategoryTaxonomy has a case that blocks and File does not.
- Q: Should admission reject a *new* `fileRef` pointing at a File that is already deleted, the way spec 052 rejects a new `categoryRef` pointing at an already-`Terminating` `CategoryTaxonomy` (its FR-014)? → A: No — spec 052's rule exists to close a race specific to its own block-and-drain model: a brand-new reference created against a category that is mid-drain and about to disappear would immediately need decoupling, so blocking the reference at the door avoids a pointless create-then-immediately-decouple sequence. File deletion has no drain window (per this session's first decision) — there is no in-between state during which a new reference could be created "just before" removal in a way that differs from creating a reference against a File that was already gone yesterday. A `fileRef` pointing at a nonexistent File already resolves async to `FileRefConfirmed=False/FileNotFound` exactly like any other never-existed reference (existing behavior, unchanged); a File-specific admission-time rejection would add a special case with no corresponding integrity benefit, so this spec introduces none.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A resource's resolved media reference is recorded as a trackable ownership link, not just a name (Priority: P1)

Today, when a `Product`, `ProductVariant`, `CategoryTaxonomy`, or `Collection` author writes `spec.media[*].fileRef` pointing at a `File`, nothing about that relationship is recorded anywhere queryable — the only fileRef-aware code in the system (`CategoryTaxonomy`'s `computeFileRefCondition`) can't even confirm the File exists, because File isn't yet queryable, so it always reports `Unknown`. Once File exists and controllers can resolve references, every resource whose reference successfully resolves must record that fact as a `metadata.ownerReferences` entry pointing at the File — this is the foundation everything else in this spec (the index, the deletion effect) is built on.

**Why this priority**: Without a recorded ownership link, there is no way to ask "what points at this File?" except scanning every resource of every kind — the O(all resources) scan this issue and `docs/implementation/034-file-media-lifecycle-architecture.md` §9 both explicitly reject. This story is the prerequisite for User Stories 2 and 3.

**Independent Test**: Can be fully tested by creating a `File` and a `Product` (or `ProductVariant`/`CategoryTaxonomy`/`Collection`) whose `spec.media[*].fileRef` names that File, waiting for the reference to resolve, and confirming the referencing resource's `metadata.ownerReferences` contains a `{kind: File, name, uid, blockOwnerDeletion: false}` entry for that File — independent of any deletion happening at all.

**Acceptance Scenarios**:

1. **Given** a `Product` with a `spec.media[*].fileRef` naming an existing, `Ready` `File`, **When** the controller resolves that reference and transitions `FileRefConfirmed` to `True`, **Then** the `Product`'s `metadata.ownerReferences` gains an entry `{kind: File, name: <file name>, uid: <file uid>, blockOwnerDeletion: false}`.
2. **Given** the same scenario for `ProductVariant`, `CategoryTaxonomy`, and `Collection` in place of `Product`, **When** each one's reference resolves, **Then** each records the same shape of `ownerReferences` entry against the same File.
3. **Given** a resource with multiple `spec.media` entries pointing at different Files, **When** each reference resolves independently, **Then** the resource accumulates one `ownerReferences` entry per resolved File, and an unresolved entry contributes no `ownerReferences` entry until it, too, resolves.
4. **Given** a `spec.media[*].fileRef` whose `optional` flag is `true` versus `false`, **When** either kind of reference resolves, **Then** both write the identical `blockOwnerDeletion: false` entry shape — the `optional` flag affects only the status-condition behavior in User Story 3, never whether or how the `ownerReferences` entry is written.

---

### User Story 2 - Anyone can find every resource that references a given File, without scanning the whole catalog (Priority: P1)

An operator, an integration, or — most importantly — the future File Controller described in `docs/implementation/034-file-media-lifecycle-architecture.md` (Phase 2) needs to answer "which resources reference this File?" in order to notify or re-reconcile exactly those resources when the File's own state changes (including deletion). That answer must come from an indexed lookup, not a scan of every `Product`/`ProductVariant`/`CategoryTaxonomy`/`Collection` in the system.

**Why this priority**: Equal in importance to User Story 1 — recording the link (US1) is only useful if it can be queried back out efficiently. This is also the mechanism User Story 3's deletion behavior depends on to know which resources to act on.

**Independent Test**: Can be fully tested by creating a File referenced by a known set of resources (across more than one kind) and unrelated resources that do not reference it, then querying the reverse-reference lookup for that File's UID and confirming the result set is exactly the referencing resources — no more, no fewer — with cost independent of the total number of unrelated resources in the system.

**Acceptance Scenarios**:

1. **Given** a File referenced (with a resolved `ownerReferences` entry, per User Story 1) by three resources of different kinds, and one hundred unrelated resources that do not reference it, **When** the reverse-reference lookup is queried for that File's `uid`, **Then** it returns exactly those three resources and none of the unrelated ones.
2. **Given** a File referenced by zero resources, **When** the reverse-reference lookup is queried for that File's `uid`, **Then** it returns an empty result, not an error.
3. **Given** a resource that once referenced a File and later had its `spec.media[*].fileRef` edited to point elsewhere (or removed), **When** the reverse-reference lookup is queried for the original File's `uid` after that edit takes effect, **Then** the edited resource no longer appears in the result.

---

### User Story 3 - Deleting a File degrades the resources that reference it, safely and observably, instead of leaving them silently broken (Priority: P1)

An operator deletes a `File` — perhaps it was uploaded by mistake, is being replaced, or is no longer needed. Every resource that had a resolved reference to it must be told, in an observable way, that the reference it depended on is gone, without that resource itself being blocked from existing, without silently continuing to claim a File that no longer exists, and without the deletion of the File itself being blocked by the fact that other resources still reference it.

**Why this priority**: This is the core safety gap the issue exists to close, and depends on User Stories 1 and 2 already being in place (there is nothing to notify without the recorded link and the lookup that finds it).

**Independent Test**: Can be fully tested by deleting a File that is referenced by at least one resource with a required (`optional: false`) reference and at least one resource with an optional (`optional: true`) reference, and confirming: the deletion itself succeeds regardless of either reference; the required-reference resource's status is updated to a specific, diagnosable "file deleted" state; the optional-reference resource's resolved media list simply drops the entry with no error condition; and in both cases the `ownerReferences` entry pointing at the deleted File is removed while the resource's own git-authored `spec.media` field is left untouched.

**Acceptance Scenarios**:

1. **Given** a File referenced by no resources, **When** the File is deleted, **Then** the deletion completes with no side effects on any other resource.
2. **Given** a File referenced by a resource's required (`optional: false`) media entry, **When** the File is deleted, **Then** the deletion completes (it is never rejected on account of this reference), that resource's `FileRefConfirmed` condition transitions to `False` with a reason that specifically identifies "the File was deleted" (distinct from the existing "never resolved" reason), that resource's `Ready` condition reflects this per the existing required-reference composition rule, the corresponding `ownerReferences` entry is removed, and the resource's own `spec.media[*].fileRef` field is unchanged.
3. **Given** a File referenced by a resource's optional (`optional: true`) media entry, **When** the File is deleted, **Then** the deletion completes, no new condition is emitted for that reference, the corresponding entry is omitted from that resource's resolved media output, the `ownerReferences` entry is removed, and that resource's `Ready` condition is unaffected by this change.
4. **Given** a resource with multiple media entries where only some point at the File being deleted, **When** the File is deleted, **Then** only the affected entries' conditions/`ownerReferences`/resolved-media output change; entries pointing at other, still-existing Files are untouched.
5. **Given** a resource whose `FileRefConfirmed` condition has transitioned to `False` with the "File was deleted" reason (Scenario 2), **When** an author later pushes an update to that resource's `spec.media[*].fileRef` (pointing at a different File, or removing the entry), **Then** the reference is re-evaluated exactly as it would be for any other `fileRef` change, with no special-casing left over from the deletion — the reason does not linger past that edit.
6. **Given** a resource whose `FileRefConfirmed` condition has transitioned to `False` with the "File was deleted" reason, **When** the controller reconciles that resource again without any author edit to `spec.media`, **Then** the reason remains "File was deleted," not regressing to the generic "never resolved" reason on a later pass.

---

### Edge Cases

- What happens to a `fileRef` created against a File that was already deleted before the reference was ever created? It resolves the same way any reference to a nonexistent File already does — asynchronously, to `FileRefConfirmed=False` with the existing "not found" reason — since it was never a resolved reference in the first place and never had an `ownerReferences` entry to remove (see Clarifications, final Q&A).
- What happens if a File is deleted while a dependent's reference to it is still `Unknown` (not yet resolved either way)? No `ownerReferences` entry exists yet for that pairing (User Story 1 only writes one once resolution succeeds), so there is nothing for the reverse-reference index to find or for the deletion path to decouple; the dependent's own next reconcile attempt finds no such File and reports the existing "not found" outcome, not the "file deleted" outcome — the "file deleted" reason (User Story 3) is specifically for references that had actually resolved.
- What happens to a File's own deletion process (its own internal cleanup of processing state, derived artifacts, or its own finalizer bookkeeping) — does this spec define that? No — that is File's own CRUD/lifecycle mechanics (GH#79/spec 051 and its own follow-on), explicitly out of scope here; this spec defines only the effect File deletion has on other resources that reference it, once File deletion happens by whatever mechanism implements it.
- What happens if two different resources reference the same File, one required and one optional? Each is evaluated independently per User Story 3's Acceptance Scenarios 2/3 — the required one gets the diagnosable condition and `Ready` impact, the optional one gets silent omission — there is no cross-resource interaction between them.
- Can a resource reference the same File through more than one media entry? Each `spec.media` entry is tracked and resolved independently (per User Story 1, Scenario 3); if two entries on the same resource happen to name the same File, each still corresponds to its own `ownerReferences` bookkeeping conceptually, though in practice a resource holds at most one `ownerReferences` entry per distinct File `uid` it references (duplicate entries for the identical target are not created).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST write a `metadata.ownerReferences` entry — `{kind: File, name, uid, blockOwnerDeletion: false}` — on a `Product`, `ProductVariant`, `CategoryTaxonomy`, or `Collection` record, for each `spec.media[*].fileRef` entry, at the point the controller resolves that reference and transitions its `FileRefConfirmed` condition to `True` (mirroring the existing async-resolution trigger already used for `ParentResolved`/`CategoryResolved`, spec 039/052). `blockOwnerDeletion` MUST be `false` unconditionally — never `true` — regardless of the `fileRef` entry's own `optional` flag, per the block-vs-decouple decision in Clarifications.
- **FR-002**: The system MUST support one `ownerReferences` entry per distinct File referenced by a resource's `spec.media` list; a resource referencing multiple distinct Files accumulates one entry per resolved File, and resolution of one entry MUST NOT depend on or block resolution of any other entry on the same resource.
- **FR-003**: The system MUST provide a reverse-reference lookup — "every resource whose `metadata.ownerReferences` contains an entry naming a given File `uid`" — answerable as an indexed query, not a scan of all `Product`/`ProductVariant`/`CategoryTaxonomy`/`Collection` records, reusing the same `ownerReferences`-keyed lookup mechanism spec 052 establishes for `CategoryTaxonomy`'s own blocking-dependent check, rather than a separate `(namespace, File.name)` index or a `spec.media[*].fileRef` name-match scan.
- **FR-004**: The system MUST NOT reject or delay a File deletion request on account of any resource's `ownerReferences` entry pointing at it, regardless of how many resources reference it or whether any of those references are `optional: false`. This supersedes the blocking `deleteFile` sketch previously described in `docs/implementation/034-file-media-lifecycle-architecture.md` §7c for the dependents-check step specifically.
- **FR-005**: The system MUST, upon a File's deletion, use the reverse-reference lookup (FR-003) to identify every resource with an `ownerReferences` entry naming that File, and, as part of reconciling each such resource, remove that specific `ownerReferences` entry (orphaning that resource with respect to the deleted File only — any other `ownerReferences` entries on the same resource, pointing at other Files or other kinds, are unaffected).
- **FR-006**: For every resource identified by FR-005 whose affected `spec.media[*].fileRef` entry has `optional: false` ("required"), the system MUST transition that entry's `FileRefConfirmed` condition to `False` with a reason that specifically and distinctly identifies "the referenced File was deleted" — distinguishable from the existing "reference never resolved" reason — without modifying the resource's git-authored `spec.media` field, which remains under Git's ownership; `ownerReferences` and status conditions are controller-managed metadata, a different field entirely.
- **FR-007**: For every resource identified by FR-005 whose affected `spec.media[*].fileRef` entry has `optional: true`, the system MUST omit that entry from the resource's resolved media output and MUST NOT emit a `FileRefConfirmed` condition for it, consistent with the existing rule that optional references never contribute a condition.
- **FR-008**: The system MUST leave a resource's `Ready` condition governed by the existing required-reference composition rule unchanged by this feature: `Ready` is affected by a required reference's `FileRefConfirmed=False` (including the new "File was deleted" reason from FR-006) exactly as it already would be for any other `FileRefConfirmed=False` reason; an optional reference's omission (FR-007) never affects `Ready`.
- **FR-009**: The "File was deleted" reason (FR-006) on a resource's `FileRefConfirmed` condition MUST persist across subsequent reconciliation passes of that resource — it MUST NOT regress to the generic "reference never resolved" reason on a later reconcile — until an author edits that resource's own `spec.media[*].fileRef` field, at which point the reference is re-evaluated from scratch like any other `fileRef` change.
- **FR-010**: The system MUST NOT write an `ownerReferences` entry for a `spec.media[*].fileRef` entry that has not yet resolved (`FileRefConfirmed` is `Unknown` or `False`); a File deleted while a reference to it is still unresolved has no corresponding `ownerReferences` entry to remove, and that resource's next reconciliation attempt reports the existing "reference not found" outcome, not the "File was deleted" outcome.
- **FR-011**: The system MUST NOT introduce any admission-time rejection of a new or updated `spec.media[*].fileRef` on account of the named File having already been deleted; such a reference resolves asynchronously to the existing "not found" outcome, per the Clarifications' final Q&A.
- **FR-012**: The reverse-reference lookup (FR-003) MUST be usable, without modification, by a future File Controller (per `docs/implementation/034-file-media-lifecycle-architecture.md` §8's Phase 2 plan) to enumerate exactly the resources affected by a given File's state change, in time proportional to the number of references to that File, not to the total number of resources in the system.

### Production Requirements *(mandatory for core-service or load-bearing changes)*

- **PR-001 Replica Safety**: The `ownerReferences` write (FR-001), reverse-reference lookup (FR-003), and deletion-triggered decouple (FR-005–FR-007) MUST behave correctly under multiple concurrently running controller-manager replicas and API replicas, and MUST tolerate a replica being replaced or restarted mid-reconcile without producing a duplicate `ownerReferences` entry, a missed decouple, or a resource stuck permanently on the pre-deletion `FileRefConfirmed=True` state — reusing the same `resourceVersion`-guarded status-write pattern already used for `CategoryTaxonomy` (spec 039/052) so a retried or resumed reconcile is idempotent.
- **PR-002 Multi-User Security**: The reverse-reference lookup (FR-003) and the `ownerReferences`/status changes it drives MUST respect existing namespace-scoped authorization — a caller or controller MUST NOT be able to discover or affect references belonging to a namespace it is not authorized to read, and cross-namespace `fileRef` resolution remains rejected exactly as it already is for other reference types in this codebase.
- **PR-003 Capacity**: The reverse-reference lookup (FR-003) and the fan-out it drives (FR-005–FR-007) MUST scale with the number of references to a specific File (O(references)), not with the total number of `Product`/`ProductVariant`/`CategoryTaxonomy`/`Collection` records in the namespace or system, consistent with the "millions of Files, many dependents per File" scaling requirement `docs/implementation/034-file-media-lifecycle-architecture.md` §13 already documents.
- **PR-004 Backpressure**: Fan-out triggered by a single File's deletion (FR-005) MUST be processed in bounded batches rather than as one unbounded operation per File, and a burst of File deletions MUST NOT starve unrelated reconciliation work in the same controller-manager instance, consistent with the batching/worker-pool approach already used for other reconcilers in this codebase.
- **PR-005 Recovery**: After a partial failure during File-deletion fan-out (e.g., some but not all referencing resources have had their `ownerReferences` entry removed and condition updated before a crash or restart), the system MUST converge to the fully-decoupled state described in FR-005–FR-007 for every referencing resource on subsequent reconciliation, without requiring manual intervention and without ever reverting an already-decoupled resource back to claiming the deleted File.

### Key Entities

- **`metadata.ownerReferences` entry (File-targeting)**: A controller-managed metadata field (never git-authored) recording `{kind: File, name, uid, blockOwnerDeletion: false}` on a `Product`, `ProductVariant`, `CategoryTaxonomy`, or `Collection` record for each of its resolved `spec.media[*].fileRef` entries. `blockOwnerDeletion` is always `false` for File-targeting entries — File deletion is never blocked by these entries' existence, unlike the `blockOwnerDeletion: true` entries spec 052 defines for `CategoryTaxonomy` parent/child relationships. Written once by the controller at resolution time (FR-001), removed once by the controller at File-deletion time (FR-005).
- **Reverse-reference lookup**: A query for "every resource with an `ownerReferences` entry naming File `uid` X" — the mechanism both the deletion-effect behavior (User Story 3) and the future File Controller's fan-out (doc 034 §8, Phase 2) consume. Reuses the same `ownerReferences`-keyed indexed-lookup shape spec 052 establishes for `CategoryTaxonomy`, rather than a separate index.
- **`FileRefConfirmed` condition (File-deletion reason)**: The existing Product/ProductVariant/CategoryTaxonomy/Collection status condition (already implemented in `gitstore-controller-manager/internal/categorytaxonomy/fileref.go` and `conditions.go`, and documented — under this same name, not the stale `MediaResolved` name some ADRs still use — in `docs/implementation/034-file-media-lifecycle-architecture.md` §10) that this spec extends with a new, specific reason for "the referenced File was deleted after this reference had already resolved," distinct from the pre-existing "reference never resolved" reason.
- **Resolved media output**: The per-resource list of successfully resolved media/file references exposed in each resource's resolved status (mirroring the existing `ResolvedFileDefinition`/`resolved.media` shape referenced in doc 034 §10); an optional reference to a deleted File is silently omitted from this list (FR-007), never represented as an error entry.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of resolved `spec.media[*].fileRef` relationships (across `Product`, `ProductVariant`, `CategoryTaxonomy`, and `Collection`) have a corresponding `metadata.ownerReferences` entry with `blockOwnerDeletion: false`, and the reverse-reference lookup (FR-003) is answerable via a single indexed query rather than a scan of any resource kind's full record set.
- **SC-002**: 100% of File deletions succeed regardless of how many resources reference the File being deleted or whether any such reference is required (`optional: false`) — zero instances of a File deletion being rejected on account of a referencing resource.
- **SC-003**: 100% of resources with a required (`optional: false`) reference to a deleted File report a `FileRefConfirmed=False` condition with a reason specifically identifying "the File was deleted," distinguishable from "the reference never resolved," within one reconciliation pass of the deletion taking effect.
- **SC-004**: 100% of resources with an optional (`optional: true`) reference to a deleted File have that entry omitted from their resolved media output, with zero new error conditions emitted and zero impact on their own `Ready` condition.
- **SC-005**: Zero instances, across all deletion outcomes, of a resource continuing to carry an `ownerReferences` entry pointing at a File that no longer exists, more than one reconciliation pass after the deletion.
- **SC-006**: Zero instances of a resource's `FileRefConfirmed=False/"File was deleted"` reason regressing to the generic "never resolved" reason absent an author edit to that resource's own `spec.media[*].fileRef` field.
- **SC-007**: The reverse-reference lookup's query cost scales with the number of references to the specific File queried, not with the total number of resources in the namespace or system, verified at a scale of at least hundreds of unrelated resources alongside a small number of actual references.

## Assumptions

- **File exists as a queryable, resolvable resource by the time this spec's behavior applies.** GH#79/spec 051 defines File's schema only (no CRUD mutations, no controller-driven `SourceResolved`/`Ready` resolution yet); this spec assumes that follow-on work — File's CRUD mutations (including a working delete path) and the controller-side resolution that transitions `FileRefConfirmed` to `True` for referencing resources — exists or is delivered alongside this spec's own implementation. This spec defines the deletion-safety *behavior* those mutations and that resolution must apply, not their own request/response mechanics, admission validation, or File's own internal finalizer/cleanup bookkeeping.
- **The `metadata.ownerReferences` + `blockOwnerDeletion` mechanism (including the indexed "find by target uid" lookup) is established by spec 052 (GH#243) and reused here, not rebuilt.** Spec 052 is the first specification to make `ownerReferences` a real, populated, queryable mechanism for `CategoryTaxonomy`; this spec assumes that mechanism lands (or lands together with this spec's own implementation) and extends it to File-targeting entries rather than introducing a second, competing reference-tracking mechanism.
- **The condition type name is `FileRefConfirmed`, not `MediaResolved`.** `docs/ADRs/0004-product-lifecycle.md`, `0005-product-variant-lifecycle.md`, `0006-category-taxonomy-lifecycle.md`, and `0007-collection-lifecycle.md` each describe a planned `MediaResolved` condition, but the actually shipped implementation (`gitstore-controller-manager/internal/categorytaxonomy/fileref.go`/`conditions.go`, spec 039) and the living architecture document (`docs/implementation/034-file-media-lifecycle-architecture.md` §10) both use `FileRefConfirmed` throughout. This spec reuses `FileRefConfirmed` for consistency with what is actually implemented; updating the four ADRs' stale terminology to match is a reasonable follow-up but not required by this spec.
- **`docs/implementation/034-file-media-lifecycle-architecture.md` §7c's blocking `deleteFile` sketch is superseded, for the dependents-check step only, by this spec's decouple-always decision** (see Clarifications). File's own internal deletion mechanics — finalizer bookkeeping for cancelling in-flight processing, removing derived artifact pointers, and the eventual hard-delete of its own record — are unaffected by this correction and remain out of scope of this spec (File-CRUD territory, GH#79/spec 051's follow-on).
- **The `optional`/required distinction on `spec.media[*].fileRef` continues to mean exactly what `docs/implementation/034-file-media-lifecycle-architecture.md` §10 already documents** (gates the dependent's own `Ready` condition, nothing more) — this spec does not redefine or overload that flag's meaning.
- **`MediaAsset` (GH#316) is out of scope**, per this issue's own scope boundary; this spec's `ownerReferences`/reverse-reference mechanism is defined only for direct `fileRef → File` relationships, matching the current schema. If `MediaAsset` is introduced later as an indirection layer, its own reference-tracking needs are that future work's concern, not this spec's.
- **Binary upload, checksum verification, and processing-pipeline execution remain out of scope**, per GH#378 and per spec 051/ADR-0008's phased plan; this spec concerns only the reference-tracking and deletion-effect behavior layered on top of File's existence, not File's own binary lifecycle.
