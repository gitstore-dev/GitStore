# Capacity, Failure and Contract Acceptance (Proposed)

No workload, deployment or fault in this document has been run by planning. Each phase first adds tests, demonstrates the expected failure, then implements its minimum contract. Read current tests/capacity and tests/chaos instructions before extending runners; protect retained fixtures/storage/evidence.

## Healthy workload

Use existing `make capacity TARGET=api PROFILE=endpoint-split MODE=<diagnostic|alpha|production>`, `TARGET=namespace PROFILE=watch`, `TARGET=repository PROFILE=lifecycle`. Add event/audit/outbox/receiver probes to existing runners/verifiers/mode plumbing; no feature-specific public Make targets. These probes do not exist yet. Include existing sustained native push/GraphQL authoring/reconciliation traffic and retain stricter owning profile gates; do not count log statements as successful completion.

Run phase-isolated and combined 30-minute acceptance with verified retained >=5M products/10K categories, two APIs/two controllers/one Git, provisioned source and backend retention storage. Use plan.md allocations (Scylla RF3, >=6 TiB/node) and record actual CPU/RSS/disk/IOPS/network, source checksum state and process epochs. Production delivery additionally records Svix deployment/version/account quotas, effective policy, retention, service latency and bounded provider-call/status concurrency. A controlled provider fixture proves adapter failure behavior; the production Svix receiver run proves end-to-end compatibility. Dev runs cannot substitute. No OOM/unexpected restart, <=80% sustained CPU/<=80% assigned memory, >=20% disk headroom after modeled quotas, no steadily growing healthy backlog.

- Event: 500 offered calls/s across 8 producers/two namespaces; 25% exact idempotent retries. Of 375 new observations/s, 90% aggregate over 64 stable series, 10% create distinct series. Rotate producer series names every15 minutes. Normal body256 B/full summary<=1 KiB, plus separately attributed 4 KiB/body and16 KiB/full-record boundary probes. Count oracles distinguish request, unique observation and series, including retained retries.
- Audit: 100 audited operations/s with declared required/async mix and up to two <=1 KiB records/operation. Verify actual coverage and truthfulness, not merely append rate.
- Resource/Git: 100 eligible resource transitions/s plus10 committed Git mutations/s across <=16 active repositories, half native push/half commit-delete-tag RPC paths. Materialize110 facts/s; route90 resource+10 Git facts/s to exactly one of20 subscriptions each, and deliberately route the remaining10 resource facts to no subscriber. This yields100 delivery attempts/s without pretending every fact matches all20. Separately test maximum64-destination fan-out at a bounded lower source rate; never hide multiplicative queue cost.
- Normal fact/wire<=2 KiB; independent64 KiB-data/80 KiB-wire boundary tests. Receiver fixture records end-to-end latency, envelope equivalence and signature verification for both adapters and accepts healthy requests promptly; slow/error cases are separate. Count provider submissions/acceptances, HTTP attempts and confirmed receiver receipts independently; no assumption that one submission equals one attempt.
- Healthy p95/p99: Event/audit acceptance<=250 ms/1 s; eligible source-to-fact<=1 s/3 s; ready delivery-to-receiver<=2 s/5 s; unexpected errors<1%. No silent accepted-work loss, cross-scope leakage, incorrect count, duplicate logical fact or unreported source gap. Source-to-receiver measurement includes routing/queueing.

Source/journal work includes internal Event marker/progress frames, not just exported facts. Bound diagnostics ingestion so it cannot starve resource materialization; measure ordinary reconciliation/watch freshness under the combined mix. Public subscriber replay limits remain explicit and may require cold initialization after declared gaps; private outbox reads have their own finite replay budget. Do not equate a successful resource relist with restored integration history.

## Storage and retention occupancy

Production provider storage/queue/replay retention quotas must also cover the declared workload; record actual limits and externally retained payload/secret custody. They are separate from the following GitStore allocations, not unlimited managed capacity.

Initial deployment hard quotas (logical retained allocations before RF3/index overhead modeling): audit<=768 GiB; outbox/configuration<=256 GiB; delivery/attempt history<=256 GiB; Event receipts/markers<=256 GiB; integration control/indexes<=64 GiB; live Event records<=100,000/namespace and<=1 GiB/namespace. Allocate existing CDC/journal/catalogue separately and validate total retained physical estimates plus >=20% headroom against provisioned volumes; quotas are not extra free space outside the datastore. Git source64 GiB global, <=8 GiB/repository default. Receipts/markers allow >=20M observations/namespace for the declared24-hour mix; inactive/terminal retention cleanup must be proven with controlled clocks and maximum-occupancy fixtures, not only an empty-store benchmark.

At100 facts/s,64 KiB each is ~527 GiB/day before replication; at110/s it is ~580 GiB/day. The normal2 KiB mix and max-size probes are different workloads. Long retention of the maximum-size workload will hit finite quotas and must throttle/degrade explicitly at the declared boundary, not be advertised as unlimited sustainable acceptance. Record actual encoded row/CDC preimage/postimage/index/receipt bytes and retained duty cycle. One-hour live Event TTL does not remove fourteen-day CDC footprint.

## Overload and fault recovery

Five minutes at twice offered rates must keep worker/queue/storage bounds and accepted-work correctness. Diagnostics can reject/drop under declared counters; required accepted facts cannot disappear. Healthy acceptance/freshness returns<=30 s after overload removal; residual backlog is independently verified. For a controlled five-minute materializer/receiver outage, bound injected backlog to33,000 facts/30,000 deliveries. Qualify recovery capacity>=220 facts/s against110/s offers and>=200 deliveries/s against100/s offers, draining each<=300 s after readiness. Do not infer drain rate from worker count.

Reuse owned api-restart/controller-restart/journal-interruption profiles with explicit target/ownership confirmation. Add precise test-owned receiver/storage failure and non-overlapping Git replacement through existing harness helpers, not broad process cleanup or a new standalone runner. API lease expiry during provider acceptance and delayed provider observations require a controlled provider/receiver/process barrier. Include response loss at submission and redelivery, credential failures, provider outage/429, exhausted idempotency horizons, and unconfirmed disable/cancellation. No blind cross-provider failover. Process restored does not mean domain recovered. Healthy processing resumes<=60 s after dependencies are ready or an existing stricter deadline; cold list recovery retains its owning measured bound and all admitted pending work. Bound status polling staleness to30 s under healthy dependencies; preserve uncertainty and degraded conditions during outages. Source-expiry tests deliberately declare coverage gaps.

Verify single Git/no overlapping storage writers, separate controller checkpoint directories, all API replicas' decisions, bounded API provider calls/queues, provider-managed delivery limits and polling freshness, exact source/config/generated schema/action versions and accepted/dropped/completed receipts. Preserve expensive baseline and unrelated evidence; no reseed/down-volume shortcut. Full default `make pr-ready`, normal generated-source checks and meaningful backend tests remain required before implementation PRs. Capacity does not replace them or certify host/power-loss Git durability.

## Release/lifecycle evidence

Additive schema/storage/RPC rollout remains inactive until compatible recipients and owned source feeds are ready. Test old/new API/controller overlap and non-overlapping Git replacement; unsupported old RPC/floor remains explicitly unavailable. Rollback disables new acceptance, retains all tables/source logs/required work, drains or records explicit cancellations and routes only compatible clients. No destructive down migration.

Amend design039 and datastore-only inventory, then explicitly assess ADR0015/0018 core-decision implementation in the implementing PR. Where the core is now in force, include its Accepted(date) status/index change using the actual permitted date; otherwise retain Proposed with the remaining core gap. Close child/umbrella issues only on their own completed implementation/evidence.
