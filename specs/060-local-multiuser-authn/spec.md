# Feature Specification: Local Multi-User AuthN + UserDir Provider (`static-users`)

**Feature Branch**: `060-local-multiuser-authn`

**Created**: 2026-08-29 (revised 2026-09-01)
**Status**: Draft
**Input**: User description: "GitStore's `rbac-local` AuthZ provider already supports mapping multiple subjects to roles via `role_bindings`, but no real AuthN provider today can authenticate more than one distinct human identity — `static-admin` structurally supports exactly one hardcoded admin credential. Ship a new AuthN provider that authenticates against a config-driven list of username + bcrypt password-hash pairs. **Revision**: don't add it as a sibling to `static-admin` — remove `static-admin` entirely and have the new provider (`static-users`) replace it fully. 'Admin' becomes just a role grantable to one or many users via the already-existing `role_bindings` mechanism, no new admin-specific code path. `static-users` implements both AuthN and UserDir, since real multiple users make user metadata (email/display name) worth giving a real home. Work through, and show the reasoning for: the migration path for existing `static-admin` deployments (automatic env-var fallback vs. a documented clean breaking change, given this project's pre-stable alpha phase); re-verifying that `static-admin`'s traced hardcoded-admin-role bypass disappears with it, meaning post-migration admin access flows exclusively through a real `role_bindings` entry — and making sure the migration story doesn't let someone migrate and silently lose admin access; the full removal scope (every reference to `staticadmin`/`static-admin`, including the `make gen-admin-password` Makefile target); and whether the previously-planned `ChainedAuthN.IssueSessionFor` registry addition is still needed once `static-admin` no longer coexists in the chain. Separately, and found from direct operator experience: some auth env vars (JWT secret, admin password hash, and a third one) cause an unconditional startup failure today regardless of whether the corresponding provider is even chained in — fix this as part of the same config-validation surface this spec already touches, scoping the fix precisely to which env vars are actually provider-specific vs. genuinely always required."

## Clarifications

### Session 2026-08-29 (first pass)

- Q: Does `rbac-local` need any code change to support multiple real subjects? → A: No, confirmed by reading `gitstore-api/internal/auth/provider/rbaclocal/provider.go` and `policy.go` in full — `Policy.RoleBindings` already maps an arbitrary subject string to roles with no provider-specific assumption. Re-confirmed unchanged after this revision (research.md Decision 9).
- Q: How does this relate to spec 059 (optional reference OIDC provider)? → A: Complementary, not competing, unchanged by this revision. `gitstore-api`/`gitstore-git-service`/`gitstore-controller-manager` are GitStore's only *mandatory* components; spec 059's Hydra+Kratos stack is optional, bring-your-own-or-build-your-own infrastructure for operators who want a real, standards-compliant IdP. This spec is the always-available, zero-optional-dependency local-identity path — for the mandatory core components' own security-boundary test suites, and for small deployments that want more than one named account without a full IdP.

### Session 2026-08-29 (revision)

- Q: Should `static-users` coexist with `static-admin`, or replace it? → A: **Replace it entirely.** `gitstore-api/internal/auth/provider/staticadmin/` is deleted. "Admin" is no longer a distinct code concept anywhere — it becomes purely a role name in `rbac-local`'s `policy.yaml`, grantable to any subject (including zero, one, or many `static-users` identities) through the already-existing `role_bindings` map. See research.md Decisions 1–2.
- Q: Does removing `static-admin` reintroduce, in a new form, the privilege-escalation risk the first draft traced in its bearer-token verification path? → A: No — that risk (any token verifying against `static-admin`'s secret/issuer getting a blanket, subject-independent `admin` role) is *eliminated*, not relocated, because there is no more hardcoded role assignment anywhere. The new risk this revision must guard against is the opposite failure direction: since "admin" now flows *exclusively* through `role_bindings`, a migration that changes the credential mechanism without also adding the matching `role_bindings` entry silently produces a locked-out operator, not a privilege escalation. See Clarification below and research.md Decision 5.
- Q: Given `docs/runbooks/release-process.md`'s alpha-phase framing (no stable release exists yet) and this codebase's own prior precedent (spec 030, spec 046 both invoke Constitution Principle III to treat pre-stable removals as non-breaking; `cmd/gitctl` already replaced `cmd/hashpw` cleanly per this codebase's own recorded history) — does `static-users` need to auto-migrate `GITSTORE_AUTH__ADMIN__USERNAME`/`GITSTORE_AUTH__ADMIN__PASSWORD_HASH` at runtime, or is a documented, clean breaking change acceptable? → A: **Clean breaking change, no runtime auto-migration.** Both project-wide precedent and a structural reason specific to this feature support this: an auto-migrated credential would still need a matching `role_bindings` entry in a *separately owned* config file (`rbac-local`'s `policy.yaml`) to be usable, and auto-writing into another provider's policy file from inside `static-users`' own startup path is a layering violation this spec is specifically trying to move away from, not reproduce in a new form. See research.md Decision 4.
- Q: Does the migration therefore need an explicit safety mechanism so an operator cannot silently end up locked out? → A: Yes — a startup validation that fails fast (not merely warns) when `static-users` and `rbac-local` are both active but zero configured `static-users` usernames appear anywhere in `role_bindings`. See FR-013 and research.md Decision 5.
- Q: Is `static-users`' previously-planned dedicated JWT secret and the additive `ChainedAuthN.IssueSessionFor` registry method still needed? → A: No to both, and for the same underlying reason: both existed solely to keep `static-users` safe *while coexisting with* `static-admin` in the same chain. With `static-admin` removed, `static-users` is the only local, token-minting AuthN provider in any currently-designed chain (`anonymous` never mints tokens; the unimplemented `oidc-jwt` provider is documented to leave issuance/refresh to the external IdP). `static-users` simply takes over the existing `auth.jwt.*` config keys unchanged. See research.md Decisions 4 (superseded) and 8.
- Q: Should `static-users` implement `UserDirProvider`, and does anything need to consume it? → A: Implement the read half (`GetBySubject`, `ListGroups`, `SearchUsers`) now, backed by two new optional `users.yaml` fields (`display_name`, `email`) — real multiple users make this metadata worth a home, even before a consumer exists. Investigated whether anything should consume it today (`createdBy`/`updatedBy` on `Repository`/`Namespace` are the natural candidates): found they are plain `String!` fields with no richer type to resolve into, and decided *not* to change that schema in this spec — it's a separate, additive GraphQL design decision for whichever future spec actually needs richer author display. See research.md Decisions 10–11.
- Q: What's the exact removal scope? → A: Enumerated exhaustively by grep, categorized, and disposed of file-by-file in research.md Decision 7 — the provider package itself, production wiring (`server.go`, `config.go`), every test that imports/constructs `staticadmin`, every test that merely uses the string `"static-admin"` as a label (relabeled for hygiene), generated code (explicitly left alone, per this project's own "never hand-edit generated files" convention), and documentation both in- and out-of-scope for this spec (this spec's own docs vs. a flagged, not-edited-here impact on spec 021's still-unimplemented premise).
- Q: Separately reported from direct operator experience — do any auth env vars cause an unconditional startup failure regardless of which AuthN provider is chained in? → A: Yes, confirmed by reading `gitstore-api/internal/config/config.go`'s validation code directly: `auth.jwt.secret` (tied specifically to the local credential provider — `static-admin` today, `static-users` after this spec) and `auth.admin.username`/`auth.admin.password_hash` (moot once `static-admin`'s config is deleted) are both unconditionally `validate:"required"` today, regardless of `auth.authn.chain`'s contents. The suspected "third one," `auth.grpc.hmac_secret`, is also unconditionally required today, but *correctly* so — it protects API↔git-service gRPC trust, unrelated to end-user AuthN provider choice — and is explicitly ruled out of this fix. See FR-014/FR-015 and research.md Decision 12.

### Baseline update 2026-09-01

The implementation baseline has moved since this specification was first
written. `main` now has an explicit `auth.userdir.provider` configuration
selector, explicit configuration-file loading for the local Compose profile,
and the durable Namespace watch contract (including the `namespace.watch`
authorization action). This specification therefore treats UserDir selection
as an explicit provider choice: `static-users` becomes a valid
`auth.userdir.provider` value and must be configured alongside the AuthN chain
when UserDir lookups are desired. It must not silently override an explicitly
selected UserDir provider. The shared `config/config.toml` and read-only local
Compose mounts are current deployment inputs; the migration tasks update that
file and add the API-only `users.yaml` mount accordingly. Namespace-watch
behavior remains out of scope, but existing policy actions such as
`namespace.watch` must be preserved when updating role bindings.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - An operator configures multiple named local users who can each authenticate with their own credentials (Priority: P1)

An operator running GitStore without a full IdP wants more than one real, distinct human identity to be able to log in — for example, to test namespace isolation between two users, or to run a small deployment with a handful of named local accounts instead of one shared admin credential. They list each user (a username and a bcrypt password hash, optionally a display name and email) in a config-driven file, and each listed user can log in with their own credentials and receive a bearer token carrying their own subject.

**Why this priority**: This is the entire reason this spec exists — without it, there is no real AuthN provider capable of producing more than one distinct authenticated identity anywhere in the mandatory core components, and (after this revision) it is now also the *only* local credential-based AuthN provider GitStore ships at all.

**Independent Test**: Can be fully tested by configuring two users in `static-users`, calling the `login` mutation with each user's own username/password, and confirming each returns a valid token whose subject matches that user and no other.

**Acceptance Scenarios**:

1. **Given** a `static-users` configuration listing users `alice` and `bob` with distinct bcrypt password hashes, **When** `alice` logs in with her own username and password, **Then** authentication succeeds and the issued token's subject is `alice`.
2. **Given** the same configuration, **When** `bob` logs in with `alice`'s password, **Then** authentication fails.
3. **Given** the same configuration, **When** a username not present in the list attempts to log in, **Then** authentication fails without revealing whether the username exists.
4. **Given** a deployment with only one configured user (the smallest possible `static-users` configuration), **When** that user logs in, **Then** the experience is exactly as simple as `static-admin`'s single-credential login was — supporting many users does not make supporting one user any harder.

---

### User Story 2 - `rbac-local`'s existing multi-subject `role_bindings` become exercisable end-to-end for the first time, and are now the *only* place any role — including "admin" — is granted (Priority: P1)

An operator wants distinct, really-authenticated users to receive different roles from `rbac-local`'s policy — for example, `alice` bound to `admin`, `bob` bound to `developer` — and have those roles actually determine what each can do, using nothing but the mandatory core components. Because `static-users` never hardcodes a role (unlike the now-removed `static-admin`), `role_bindings` is not just *exercisable* now, it is *load-bearing*: it is the sole mechanism by which any administrative access exists at all.

**Why this priority**: Equal in importance to User Story 1. Removing `static-admin`'s hardcoded role assignment (rather than merely adding a second provider that never had one) is what finally makes `role_bindings` the single source of truth for authorization roles in this codebase, closing a gap that existed even in the first draft of this spec (which would have left `static-admin`'s hardcode in place, coexisting with, but not integrated into, `role_bindings`).

**Independent Test**: Can be fully tested by binding two `static-users` identities to two different roles in `policy.yaml`'s `role_bindings`, authenticating as each, and confirming their authorization outcomes differ according to their bound roles — using only the existing, unmodified `rbac-local` provider — and separately by confirming that a `static-users` identity with *no* `role_bindings` entry is denied every action `rbac-local`'s `default_deny` would deny to any unbound subject.

**Acceptance Scenarios**:

1. **Given** `role_bindings` mapping `alice` to `admin` and `bob` to `developer`, **When** each authenticates via `static-users` and attempts an action only the `admin` role permits, **Then** `alice`'s attempt is allowed and `bob`'s is denied.
2. **Given** a `static-users` identity with no `role_bindings` entry, **When** it attempts any action under `rbac-local` with `default_deny` true (the default), **Then** the action is denied — there is no other path by which that identity could be granted a role.
3. **Given** any `static-users` principal, **When** its `Roles` field is inspected directly (for example via `Principal.IsAdmin()`), **Then** it is always empty — role information exists only inside `rbac-local`'s authorization decision, never on the principal itself. Any future code needing an authoritative "is this an admin" answer MUST call `AuthZProvider.Authorize`, never `Principal.IsAdmin()`.

---

### User Story 3 - Migrating an existing `static-admin` deployment to `static-users` never silently drops administrative access (Priority: P1)

An operator running an existing GitStore deployment configured with `static-admin` upgrades to a version of GitStore where `static-admin` no longer exists. They follow a documented migration procedure: generate a bcrypt hash for their admin credential, add it as an entry in `users.yaml`, add a corresponding `role_bindings` entry in `policy.yaml` granting that identity a role with the access they need (typically `admin`), and switch `auth.authn.chain` to `static-users`. If they forget the `role_bindings` step, the server refuses to start with a clear, actionable error rather than starting successfully and silently locking them out.

**Why this priority**: Equal in importance to User Stories 1 and 2. A migration that trades a hardcoded, always-present admin credential for a config-driven one that can be silently misconfigured into granting no one any access at all would be a strict regression in operability, not an improvement — this user story is what makes the migration safe to perform, not just possible.

**Independent Test**: Can be fully tested two ways: (a) performing the full migration procedure correctly and confirming the migrated identity retains equivalent access; (b) performing every step *except* the `role_bindings` addition and confirming the server fails to start with an error identifying the missing binding, rather than starting and silently denying every request from that identity.

**Acceptance Scenarios**:

1. **Given** a documented migration procedure followed in full (bcrypt hash generated, `users.yaml` entry added, `role_bindings` entry added, chain updated), **When** the server starts, **Then** the migrated identity can log in and retains equivalent access to what `static-admin` previously granted it.
2. **Given** `static-users` is configured with one or more users and `auth.authz.provider` is `rbac-local`, **When** none of the configured usernames appears anywhere in `policy.yaml`'s `role_bindings`, **Then** the server refuses to start, with an error identifying that no configured `static-users` identity has any role binding.
3. **Given** the same configuration but `auth.authz.provider` is `allow-all` (the default), **When** the server starts, **Then** no such check fires — `role_bindings` is irrelevant under `allow-all`, and requiring it there would misrepresent what that configuration actually needs.
4. **Given** a `policy.yaml` where at least one configured `static-users` username has a `role_bindings` entry (even if other configured usernames do not), **When** the server starts, **Then** the check passes — the safety net targets "no binding exists for anyone," not "every user has one."

---

### User Story 4 - The `test-user:` integration-test backdoor is retired in favor of real logins through `static-users`, and the harness's own admin bootstrap moves off `static-admin` too (Priority: P2)

The two-user namespace-isolation integration test (`tests/integration/authz_repository_contract_test.go`'s `TestRepositoryAuthorization_TwoUserNamespaceIsolation`) currently authenticates `alice`/`bob` using a literal `"test-user:alice"`/`"test-user:bob"` bearer-token string recognized only by a throwaway, test-only server binary's own bespoke `AuthNProvider`. Separately, that same synthetic server's *own* administrative bootstrap identity is currently built with `staticadmin.New(...)` — which no longer exists after this spec. Both migrate to real `static-users` logins.

**Why this priority**: Lower urgency than User Stories 1–3 because neither mechanism is compiled into the real service binary, but (a) the `test-user:` bypass remains a lingering unauthenticated-identity-bypass pattern worth closing, and (b) the harness's `staticadmin` usage is not optional to migrate — it is a direct, mechanical consequence of deleting the package this spec removes, since the harness would not compile otherwise.

**Independent Test**: Can be fully tested by running `TestRepositoryAuthorization_TwoUserNamespaceIsolation` (and any other test found to rely on either mechanism) after migration and confirming it passes using real, credential-authenticated `static-users` logins throughout, including for whatever identity the harness previously used as its `static-admin` bootstrap.

**Acceptance Scenarios**:

1. **Given** the migrated test harness, **When** `TestRepositoryAuthorization_TwoUserNamespaceIsolation` runs, **Then** `alice` and `bob` are authenticated via real `login` calls against two `static-users`-configured identities, not via a `test-user:`-prefixed bearer string.
2. **Given** the migrated harness, **When** any test in `tests/integration/` is searched for the literal string `test-user:`, **Then** zero matches are found.
3. **Given** the migrated harness, **When** its `AuthNProvider` chain and admin-bootstrap setup are inspected, **Then** no reference to `staticadmin`/`static-admin` remains — the harness's own bootstrap identity is a `static-users` entry with a corresponding test-fixture `role_bindings` grant, and the harness's own bespoke `namespaceOwnerAuthZ` test double (which previously checked `principal.IsAdmin()`) is updated to recognize that identity correctly, since `static-users` principals never carry a hardcoded role.

### Edge Cases

- What happens when `users.yaml` is missing, empty, malformed YAML, or fails schema validation? (Provider construction fails fast at startup, mirroring `rbac-local`'s existing `loadPolicy` fail-fast behavior.)
- What happens when two entries in the user list share the same username? (Rejected at load time as an invalid configuration.)
- What happens when an operator edits the user list to add, remove, or change a password for a user while the server is running? (Reloadable via the same SIGHUP-triggered mechanism `rbac-local`'s policy reload already uses, using the same atomic-replace (`os.Rename`) file-update discipline.)
- What happens to a `static-users` identity that is removed from `users.yaml` while it holds an unexpired token? (Existing access tokens remain valid until natural expiry or explicit `logout`/revocation, but removal immediately prevents that subject from issuing or refreshing sessions.)
- What happens when a `static-users` identity has no entry in `rbac-local`'s `role_bindings`? (Covered directly by User Story 2, Acceptance Scenario 2 — denied by `default_deny`, and covered at the fleet level by User Story 3's startup safety net.)
- What happens during the migration window if an operator sets `auth.authn.chain` to include `static-users` but has not yet written `users.yaml`? (Provider construction fails fast, per the first edge case above — this is not a distinct case, just the "missing file" case applied to a fresh migration.)
- What happens when `GetBySubject`/`ListGroups`/`SearchUsers` are called for a username not present in `users.yaml`? (A distinguishable "not found" outcome, not `ErrNotSupported` — the UserDir operation is supported, the subject simply does not exist. See research.md Decision 10.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST remove the `static-admin` AuthN provider entirely — its package, its production wiring, and every configuration key that exists solely to configure it (`auth.admin.username`, `auth.admin.password_hash`).
- **FR-002**: The system MUST provide a new AuthN provider, `static-users`, that authenticates HTTP Basic Auth credentials against a config-driven, file-loaded list of `{username, bcrypt password hash}` pairs, following the same load/validate/fail-fast/reload pattern `rbac-local` already uses for `policy.yaml`, and MUST become the sole local, credential-based provider in the default `auth.authn.chain`.
- **FR-003**: `static-users` MUST support one or more configured users with no structural upper limit, and MUST work identically simply for a single-user configuration as `static-admin` did for its one hardcoded credential (User Story 1, Acceptance Scenario 4).
- **FR-004**: `static-users` MUST NOT assign any hardcoded role to a successfully authenticated principal, under any circumstance, including for a user list of size one. Role assignment for every `static-users` identity MUST be determined entirely by the active AuthZ provider (`rbac-local`'s `role_bindings`, or whatever provider is active), keyed on the principal's bare subject string.
- **FR-005**: `static-users` MUST take over the existing `auth.jwt.*` configuration keys (`auth.jwt.secret`, `auth.jwt.issuer`, `auth.jwt.duration`, `auth.jwt.refresh_grace`) for its own session signing, unchanged in name and shape. Tokens minted by `static-users` MUST append `/static-users` to the configured issuer base unconditionally—even when that base already ends with `/static-users`; upgraded replicas MUST temporarily accept the exact legacy configured issuer so old sessions survive a rolling upgrade, while old `static-admin` replicas reject newly minted non-admin sessions.
- **FR-006**: `static-users` MUST support replica-safe `RevokeSession` (logout) and one-time `RefreshSession` rotation. Revoked JTIs MUST be stored in shared production storage through natural expiry plus verifier leeway, concurrent refresh attempts across replicas MUST allow exactly one replacement, and a removed user MUST NOT refresh an existing token.
- **FR-007**: `static-users` MUST reject two configured usernames that collide within its own user list at load time, before the provider becomes active.
- **FR-008**: `static-users`' configuration file MUST support a live reload triggered the same way `rbac-local`'s policy reload is triggered (SIGHUP), using the same atomic-replace file-update discipline, without requiring a server restart.
- **FR-009**: The `rbac-local` AuthZ provider MUST require no source code change to support multiple real `static-users` subjects, and MUST remain the sole mechanism by which any role (including any role an operator chooses to treat as "admin") is granted to a `static-users` identity — no other code path may grant a role.
- **FR-010**: `static-users` MUST implement the `UserDirProvider` interface's read methods (`GetBySubject`, `ListGroups`, `SearchUsers`) against the same `users.yaml`-loaded state, extended with optional `display_name` and `email` fields per user entry. `UpsertProfile`/`Deactivate` (the write half) MUST return `ErrNotSupported`, consistent with this feature's config-file-driven, no-mutation-API v1 scope.
- **FR-011**: The migration from `static-admin` to `static-users` MUST be documented as an explicit, operator-run procedure (credential regeneration, `users.yaml` entry, `role_bindings` entry, chain update) — the system MUST NOT read legacy `GITSTORE_AUTH__ADMIN__*` environment variables as an automatic runtime fallback.
- **FR-012**: `Makefile` MUST provide `add-user`, backed by `gitctl users add`, which hashes the supplied password and appends a new identity to `users.yaml` through a validated atomic YAML-aware write. It MUST fail rather than overwrite an existing username, MUST preserve unrelated entries and comments, and MUST only remind the operator to add `policy.yaml` authorization—it MUST NOT mutate role bindings. The lower-level `hash-user-password` helper remains available for manual credential updates.
- **FR-013**: The system MUST fail startup with a clear, actionable error when `static-users` is present in `auth.authn.chain`, `auth.authz.provider` is `rbac-local`, and none of the usernames configured in `users.yaml` has a binding whose complete effective role set permits at least one action after explicit denies are applied. The same invariant MUST be validated before a SIGHUP reload atomically replaces the active AuthN/AuthZ/UserDir set. This check MUST NOT fire when `auth.authz.provider` is any provider other than `rbac-local`.
- **FR-013a**: Every startup-time configuration failure this spec introduces or touches (FR-013's `role_bindings` safety-net check, FR-014's chain-aware `auth.jwt.secret` check, and `static-users`' own `users.yaml` load/validation failure) MUST render a multi-line, numbered remediation guide as part of the fatal error — not a single-sentence error — naming: (1) which check failed and why, in terms of the operator's own configured values (e.g., the actual configured usernames, the actual file path attempted); (2) the exact file(s) and key(s) the operator must edit to fix it (e.g., "add a `role_bindings` entry for one of: alice, bob to policy.yaml"); (3) a pointer to `quickstart.md`'s relevant manual-verification section for a worked example. This mirrors `rbaclocal.loadPolicy`'s existing single-line `fmt.Errorf`-wrapped error shape being insufficient on its own for a fail-fast check whose entire purpose is recoverability by a human operator mid-migration, per research.md Decision 5's "correct only by operator discipline" framing.
- **FR-014**: The system MUST NOT require `auth.jwt.secret` to be non-empty unless `static-users` is present in `auth.authn.chain`. This validation MUST be implemented as an explicit, imperative, chain-aware check (mirroring the existing `validateDatastoreConfig`/`validateLogFormat` pattern in `gitstore-api/internal/config/config.go`), since the underlying condition ("this specific string is one of possibly several entries in a string slice") is not expressible via the `validate:"required_if"` struct-tag mechanism already used elsewhere in that file.
- **FR-015**: The system MUST continue to require `auth.grpc.hmac_secret` to be non-empty unconditionally, regardless of `auth.authn.chain`'s contents — this key protects API↔git-service gRPC inter-service trust and is unrelated to end-user AuthN provider selection.
- **FR-016**: Any new configuration key introduced by `static-users` (e.g., the path to `users.yaml`) MUST NOT carry an unconditional `validate:"required"` struct tag; its presence/loadability MUST be enforced only at the point the provider is actually constructed (i.e., only when `static-users` is chained in), mirroring the pattern FR-014 establishes for the pre-existing `auth.jwt.secret` key.
- **FR-017**: The `test-user:`-prefixed bearer-token bypass mechanism (the `testUserAuthN` type and its embedded-source-text duplicate, both in `tests/integration/namespace_contract_test.go`) MUST be removed and replaced with a `static-users` provider configured with test fixture credentials.
- **FR-018**: Every test found (by an exhaustive `grep -rn "test-user:" tests/integration/`) to depend on the `test-user:` bypass — `tests/integration/authz_repository_contract_test.go`'s `TestRepositoryAuthorization_TwoUserNamespaceIsolation` and its helpers — MUST be migrated to authenticate through real `static-users` logins, with identical assertions about namespace-isolation behavior.
- **FR-019**: The same test harness's own administrative bootstrap setup (previously built via `staticadmin.New(...)`) MUST be migrated to a `static-users` identity with a corresponding test-fixture `role_bindings` grant, and the harness's bespoke `namespaceOwnerAuthZ` test double (which checks `principal.IsAdmin()`) MUST be updated to correctly recognize that identity given that `static-users` never sets `Principal.Roles`.
- **FR-020**: This migration MUST NOT alter or remove the unrelated `/__test/resource-body` test-only endpoint defined in the same synthetic helper server — it is a separate, non-identity-related test fixture and is out of scope.
- **FR-021**: `gitctl`'s existing `hash-password` subcommand MUST remain the documented, supported way to generate a `static-users` entry's bcrypt password hash — no new hashing tool is introduced.
- **FR-022**: The system MUST provide strict `gitctl rbac role add` / `make add-role` tooling and idempotent `gitctl rbac binding add` / `make assign-role` tooling. Both MUST preserve unrelated policy content and comments, validate the complete result, detect concurrent edits, and replace `policy.yaml` atomically. Role assignment MUST reject undefined roles and address identities as provider-neutral subjects.
- **FR-022**: `Principal.IsAdmin()`'s doc comment MUST be updated to state explicitly that it reflects only AuthN-provider-set `Principal.Roles` (always empty for `static-users`), and is not authoritative for any principal whose roles are determined by the AuthZ layer — any future code needing an authoritative admin check must call `AuthZProvider.Authorize`.

### Key Entities

- **`static-users` provider**: The sole local, credential-based `AuthNProvider` and `UserDirProvider` implementation, authenticating HTTP Basic Auth credentials against a config-driven list of local users, and serving read-only profile lookups for the same list. Fully replaces `static-admin`.
- **User list file (`users.yaml`)**: A YAML file listing `{username, password_hash, display_name?, email?}` entries, versioned (`version: v1`) and validated at load time, mirroring `rbac-local`'s `policy.yaml` file-driven convention.
- **`role_bindings` (existing, unmodified, now load-bearing)**: `rbac-local`'s existing `subject → []role` map in `policy.yaml`. After this spec, it is the *sole* mechanism by which any role — including whatever role an operator names "admin" — is ever granted to a `static-users` identity.
- **Migration procedure**: A documented, operator-run, one-time sequence (generate hash → add `users.yaml` entry → add `role_bindings` entry → update `auth.authn.chain`) for moving an existing `static-admin` deployment to `static-users`, backed by a startup safety check (FR-013) that fails loudly if the `role_bindings` step is skipped.
- **`test-user:` backdoor (retired by this spec)**: The `testUserAuthN` AuthNProvider type, scoped entirely to `tests/integration`, recognizing any `Authorization: Bearer test-user:<subject>` header as an automatically-authenticated principal.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can configure one or more distinct local users in `static-users` and have each successfully log in with only their own credentials, with 100% of cross-user credential attempts rejected.
- **SC-002**: 100% of `static-users` principals carry an empty `Roles` field regardless of what `rbac-local` grants them via `role_bindings` — role information is never duplicated onto the principal itself.
- **SC-003**: Two `static-users` identities bound to two different `rbac-local` roles via `role_bindings` produce different, correct authorization outcomes for at least one role-differentiated action, with zero `rbac-local` source changes required.
- **SC-004**: 100% of server startups where `static-users` + `rbac-local` are active and zero configured usernames have a `role_bindings` entry fail fast with an actionable error; 100% of otherwise-identical startups where at least one configured username has an entry succeed.
- **SC-005**: After migration, zero occurrences of the literal string `test-user:` remain anywhere under `tests/integration/`, and zero occurrences of `staticadmin`/`static-admin` remain anywhere the grep in research.md Decision 7 categorized as in-scope for this spec.
- **SC-006**: A server configured with `auth.authn.chain` containing only providers other than `static-users` (e.g., `["anonymous"]`) starts successfully with `auth.jwt.secret` unset; a server with `static-users` in the chain and `auth.jwt.secret` unset fails to start with an actionable error naming that key.
- **SC-007**: A server with `auth.grpc.hmac_secret` unset fails to start regardless of `auth.authn.chain`'s contents, unchanged from today's behavior.

## Assumptions

- `static-users` is scoped to HTTP Basic Auth authentication (username + password) plus the resulting bearer-token session lifecycle (issue/refresh/revoke) and read-only user-directory lookups. It is not an OIDC provider and makes no changes to `oidc-jwt`/spec 059. UserDir activation is explicit through `auth.userdir.provider=static-users`; merely placing `static-users` in the AuthN chain does not change the selected UserDir provider.
- User self-registration, a management UI, or GraphQL mutations for creating/updating/removing users remain explicitly out of scope for v1 — the user list is config-file-driven only, matching `rbac-local`'s own file-driven simplicity. `UserDirProvider`'s write methods (`UpsertProfile`/`Deactivate`) remain unimplemented for the same reason.
- Production revocation and refresh-consumption state is shared through ScyllaDB; memdb retains the same contract in process for development. Authentication fails closed when revocation state is unavailable.
- No `createdBy`/`updatedBy` GraphQL schema change is made in this spec — those fields remain plain `String!`. Wiring `UserDirProvider` into richer author display is explicitly deferred to a future spec that has a concrete requirement driving the shape of that change (research.md Decision 11).
- This spec does not modify the not-yet-implemented `docs/implementation/021-controller_service_account_auth.md` design, even though that document's "status quo" framing is built on `static-admin`-issued JWTs. That doc has since been formalized as **spec 061** (`specs/061-controller-serviceaccount-auth/`, PR #409), which owns the edit — see the Dependencies section below for the sequencing relationship this spec now carries.
- This spec is not a replacement for real production multi-tenant authentication at scale. Spec 059 (optional Hydra+Kratos OIDC stack) or a bring-your-own OIDC issuer via the already-designed `oidc-jwt` provider remains the intended production path for operators who need one; `static-users` is the lightweight, always-available, testing-and-small-deployment complement to that path.
- `docs/runbooks/production-readiness-testing.md`'s Pattern 4 (namespace-isolation/security-boundary testing) worked-example citations currently point at the `test-user:`-based test; once this spec's User Story 4 migration lands, that runbook's citations should be updated to describe the real-login-based test — tracked as a follow-up cross-reference, not performed by this spec itself.

## Dependencies

### Spec 061 (`061-controller-serviceaccount-auth`, PR #409) — release-window ordering dependency

**Raised on**: PR #405 review comment, 2026-08-29. **Resolution**: sequence spec 061 first (or in the same release window); do **not** scope a stopgap into this spec.

`gitstore-controller-manager`'s only documented way to obtain a working credential today is a `static-admin`-issued bearer JWT carrying `Roles: ["admin"]`, manually minted and pasted into `GITSTORE_CONTROLLER__API_TOKEN` (`docs/implementation/021-controller_service_account_auth.md` §2, citing `specs/040-controller-watch-status-api/research.md`'s interim decision). This spec removes `static-admin`.

**Nature of the coupling — architectural, not mechanical** (verified against the codebase in spec 061's own analysis, not assumed):

- There is **no compile-time or hard runtime break** if this spec merges first. `gitstore-controller-manager/internal/graphqlclient.Client` treats its token as an opaque bearer string (`New(baseURL, token string)`), and the `Makefile`'s `bootstrap-token` target calls the generic GraphQL `login` mutation over `curl`/`jq` with no Go-level import of `staticadmin`, `gitctl`, or any provider package. Both are provider-agnostic and work with a token minted by any active local credential provider.
- The real problem is that, without spec 061, the *only* remaining way to mint a controller credential after this spec ships would be creating a `static-users` entry — a `{username, bcrypt password_hash}` row in `users.yaml`, HTTP-Basic-Auth-shaped, designed for a **named human operator** — for a non-human controller process. That is precisely the anti-pattern doc 021 exists to eliminate (§3, Required Property #1: *"a controller must never be indistinguishable from a human admin in the audit trail"*), and it would have to be introduced by this spec's migration documentation and then torn back out once spec 061 lands.

**What this means for this spec:**

- **DEP-001**: Spec 061's User Story 1/2 (doc 021 §14 Phase 1 — persistent ServiceAccount identity, opt-in `serviceaccount-assertion`/`serviceaccount-jwt` providers, assertion-gated `issueServiceAccountToken`, ServiceAccount lifecycle mutations) SHOULD land before, or in the same release window as, this spec. Neither spec's tests depend on the other's provider existing, and their `role_bindings` surfaces are purely additive to each other (this spec adds human entries such as `alice: [admin]`; spec 061 adds machine entries such as `serviceaccount:controllers:category-taxonomy: [category-taxonomy-controller]`).
- **DEP-002**: This spec's migration documentation MUST NOT instruct operators to create a `static-users` entry for `gitstore-controller-manager`. Where an operator asks *"how do I authenticate the controller-manager now?"*, the documentation MUST point at spec 061's `serviceaccount-jwt` path. If spec 061 has not yet landed when this spec's docs are written, the documentation MUST explicitly name that as a known gap with a forward reference, rather than documenting the human-credential workaround as if it were the intended design.
- **DEP-003**: No stopgap `static-admin` shim, no controller-specific carve-out, and no `gitstore-controller-manager` code change is introduced by this spec — its "no `gitstore-controller-manager` change" scope statement (plan.md Technical Context) is retained deliberately, because the correct fix lives entirely in spec 061.
