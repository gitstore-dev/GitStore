# Research: Local Multi-User AuthN + UserDir Provider (`static-users`)

**Revision note**: this spec was substantially rewritten after its first pass. The first draft kept `static-admin` unchanged and added `static-users` as a sibling. That direction changed: `static-admin` is now **removed entirely**, and `static-users` fully replaces it. "Admin" stops being a distinct code concept and becomes purely a role name, grantable to one or many subjects through `rbac-local`'s existing, unmodified `role_bindings`. This file supersedes the first draft's Decisions 1 and 4 (provider naming and the cross-provider secret-sharing risk no longer apply once there is only one local provider) and adds new decisions for removal scope, migration, the role-binding safety net, UserDir, and a config-validation bug found and fixed along the way.

## 1. Full replacement, not a sibling

**Decision**: Delete `gitstore-api/internal/auth/provider/staticadmin/` entirely (`provider.go`, `jti.go`, `staticadmin_test.go`). `static-users` becomes the sole local, credential-based AuthN provider. The default `auth.authn.chain` becomes `["static-users","anonymous"]` (was `["static-admin","anonymous"]`).

**Rationale**: The first draft's entire justification for keeping `static-admin` untouched (FR-003 in the original spec) was to avoid touching code outside this feature's scope. But that constraint produced real, traced complexity for no lasting benefit: a second local credential provider requires a dedicated signing secret (to stop `static-admin`'s blanket "any verifying token gets `admin`" bearer path from swallowing `static-users` tokens) and a new registry-level `IssueSessionFor` routing method (to stop chain-order from misattributing which provider mints a session) — see Decision 8 below for why both of those are now unnecessary. Once the direction changed to "one local provider, many users," these workarounds evaporate along with the code they were compensating for. `static-admin`'s only reason to exist — authenticating exactly one hardcoded credential — is now a *degenerate case* of `static-users` (a `users.yaml` with one entry, bound to an `admin` role via `role_bindings`), not a separate code path worth maintaining in parallel.

**Alternatives considered**:
- *Keep both, `static-admin` as a "fast path single-admin" convenience*. Rejected — this is exactly the first draft's design, and it is strictly more code, more config surface, and (per Decision 8 below) an unnecessary security-hardening burden (the dedicated-secret/`IssueSessionFor` machinery) for a case `static-users` already covers with one `users.yaml` entry.

## 2. What "admin" means now

**Decision**: "Admin" is not a code concept anywhere in the new design. It is a *role name* in `rbac-local`'s `policy.yaml` (the existing `roles.admin: { allow: ["*"] }` entry already shown in `docs/implementation/020-pluggable_auth_architecture.md` §2d's example policy), granted to zero, one, or many subjects via the existing `role_bindings` map. `static-users`' `Principal` never carries a hardcoded role (unchanged from the first draft's FR-005) — this is what makes "admin" purely a `role_bindings` fact rather than a property of *how* someone authenticated.

**Rationale**: This is the direct, intended consequence of removing `static-admin`'s hardcoded `Roles: []string{"admin"}` assignment (traced in the first draft's now-superseded Decision 4) without replacing it with an equivalent hardcode anywhere else. It is also the change that makes `rbac-local`'s multi-subject `role_bindings` the *only* place administrative access is granted — which is precisely what makes the migration-safety concern in Decision 5 below a real, must-solve problem rather than a hypothetical one.

## 3. `Principal.IsAdmin()` is no longer reliable — and it doesn't need to be

**Finding**: `auth.Principal.IsAdmin()` (`gitstore-api/internal/auth/types.go`) checks `Principal.Roles` for the literal string `"admin"`. Since `static-users` never populates `Principal.Roles` (Decision 2), `IsAdmin()` returns `false` for *every* `static-users` principal, even one `rbac-local`'s `role_bindings` grants the `admin` role to — `role_bindings`-derived roles exist only transiently inside `RBACLocalProvider.Authorize`'s local `effectiveRoles` slice; they are never written back onto `Principal.Roles`.

**Decision**: Do not fix this by writing `role_bindings`-derived roles back onto `Principal` (that would require a synchronous callout to the AuthZ provider anywhere a `Principal` is constructed, well outside the AuthN plane's concern, and it isn't necessary — see below). Instead, confirm and document that `Principal.IsAdmin()` was already dead code on every live (non-test) code path: an exhaustive `grep -rn "\.IsAdmin()\|isAdmin" gitstore-api --include="*.go"` excluding generated/test code returns zero calls outside generated GraphQL scaffolding for the `User.isAdmin` field (itself dead — no resolver ever constructs a `model.User`; `LoginPayload` returns only `token`). Both of the two isAdmin checks the pluggable-auth migration set out to replace were already migrated to `authz.Authorize` calls in Phase 2 (`020-pluggable_auth_architecture.md` §3b, marked ✅ COMPLETE). `Principal.IsAdmin()` itself is documented (this spec adds a doc comment) as **not authoritative for any provider that defers role assignment to the AuthZ layer** — any future code needing an "is this principal an admin" answer must call `AuthZProvider.Authorize`, never `Principal.IsAdmin()`.

**One real, in-scope exception**: the test-only `namespaceOwnerAuthZ` double in `tests/integration/namespace_contract_test.go` *does* call `principal.IsAdmin()` today (`if principal.IsAdmin() { return Allow(...) }`) to grant its bootstrap identity blanket access. Since that identity is migrating from `static-admin` to `static-users` as part of this spec's backdoor-retirement work anyway (Decision 7), this one real caller is fixed in the same change — see `contracts/backdoor-retirement.md`. It is a test double, not `rbac-local`, so this is a one-line fix to already-being-touched test code, not a new production concern.

## 4. Migration path: clean breaking change, not a runtime env-var fallback

**Decision**: No runtime auto-migration. `static-users` never reads `GITSTORE_AUTH__ADMIN__USERNAME`/`GITSTORE_AUTH__ADMIN__PASSWORD_HASH` as an implicit fallback. Migration is an explicit, documented, operator-run, one-time step (tooling described in Decision 6), performed once per deployment when upgrading past this spec.

**Rationale, weighed against the alternative**:
- *Precedent for accepting breaking changes pre-stable*: the project is at `0.1.0-alpha.2` (`docs/runbooks/release-process.md`: "Before any stable release exists, `latest` tracks whichever alpha/beta build was published most recently" — no stable release exists yet). Constitution Principle III (Clear Contracts & Versioning) has already been invoked twice for exactly this reasoning: spec 030's research.md states verbatim, *"Removing a field that was never shipped in a stable version is not a breaking change"*, and spec 046's plan.md states, *"Backward compatibility with the unshipped legacy Namespace Scylla table and mutation input shape is explicitly not required."* This spec's removal of `static-admin` fits the same pattern precisely: `GITSTORE_AUTH__ADMIN__*` has never appeared in a stable (non-prerelease) release.
- *Direct in-repo precedent for a clean tool replacement, not a compatibility shim*: `CLAUDE.md`'s own recorded history for spec `033-auth-phase-4` states, *"`cmd/gitctl` replaces `cmd/hashpw`"* — a prior instance of exactly this codebase choosing "replace the old tool cleanly, document the new one" over maintaining both or auto-bridging between them.
- *The auto-fallback alternative was seriously considered, not dismissed out of hand*: an initial design considered having `static-users`, when `users.yaml` is absent, synthesize a single in-memory user from the legacy `GITSTORE_AUTH__ADMIN__*` env vars if still set. This was rejected for a concrete, structural reason, not just "unnecessary given precedent": Decision 5 below requires that a migrated identity also gain a `role_bindings` entry, and `role_bindings` lives in `rbac-local`'s independently-loaded `policy.yaml` — a *different provider's* config file. An auto-fallback that synthesizes a user but not its role binding would reintroduce, in a new form, the exact "administrative access granted by something invisible in the AuthZ policy file" problem this whole spec exists to eliminate from `static-admin`'s hardcoded `Roles: []string{"admin"}`. Auto-writing into another provider's policy file at runtime (rather than at an explicit, operator-reviewed migration step) was rejected as materially riskier than requiring one documented manual step.

**Alternatives considered**:
- *Runtime env-var fallback, no role_bindings synthesis* (i.e., silently grant the migrated user only whatever `default_deny`/no-binding behavior falls out). Rejected — this is precisely the silent-lockout failure mode Decision 5 exists to prevent; it would make the "migration" itself the bug.
- *Runtime env-var fallback + auto-write a `role_bindings` entry into `policy.yaml`*. Rejected — see above: mutating a second provider's independently-owned config file from inside `static-users`' own startup path is a layering violation (the AuthN provider would need write access to, and knowledge of, the AuthZ provider's file format) and turns a one-time, reviewable migration into an ongoing, implicit runtime behavior no one asked for after the first boot.

## 5. The role_bindings safety net (migration-safety-critical)

**Decision**: Add an explicit startup validation: when `static-users` is present in `auth.authn.chain` **and** `auth.authz.provider` is `rbac-local`, the server logs a fatal startup error (not merely a warning) if **none** of the usernames configured in `users.yaml` appears as a key in the loaded `policy.yaml`'s `role_bindings` map.

**Rationale**: This is the direct fix for the exact hazard named in this revision's brief: *"if the migration path doesn't also ensure a corresponding `role_bindings: <migrated-subject>: [admin]` entry exists, someone could migrate and silently lose all admin access."* Once `static-admin`'s hardcoded role assignment is gone (Decision 2), the *only* way any `static-users` identity gets any role at all is a `role_bindings` entry — so "zero configured usernames have any `role_bindings` entry" is an unambiguous, always-wrong configuration under `rbac-local`: every `static-users` login would authenticate successfully and then be denied every single action by `rbac-local`'s `default_deny` (which defaults to `true` when unset — `rbaclocal/policy.go`'s `loadPolicy`). There is no legitimate deployment shape where an operator *intends* this combination — it is always a forgotten migration step, not a valid configuration choice, which is exactly the profile of error this codebase already treats as fail-fast elsewhere (`rbaclocal.loadPolicy`'s strict schema validation, `staticadmin.New`'s — now `staticusers.New`'s — required-secret checks). A silent warning was considered and rejected: a warning is easy to miss in startup log output during exactly the migration moment when it matters most, which is the same "correct only by operator discipline, not by construction" failure mode research already rejected once in this spec's first draft (Decision 4's `IssueSessionFor` reasoning).
  - *Scope note on what the check does and does not prove*: it only confirms *some* `role_bindings` entry exists for *some* configured username — it does not verify that entry's bound role actually grants any capability (a role bound with an empty `allow` list would still pass this check and still leave that user locked out). Fully proving "at least one user can do something" would require evaluating the policy's action vocabulary, which is a materially larger, separate concern. This check is deliberately scoped to the one failure mode Decision 5 exists to close: *no binding at all*, i.e., the literal "forgot the migration step" case.
  - *Scope note on why `allow-all` is excluded*: the check only fires when `auth.authz.provider == "rbac-local"`. Under the default `allow-all` AuthZ provider, `role_bindings` is irrelevant (every action is permitted regardless), so the check would be meaningless — and forcing every `static-users` username into a `role_bindings` entry it will never use would misrepresent what `allow-all` deployments actually need.

**Alternatives considered**:
- *Log a warning, not a fatal error*. Rejected — see "correct only by operator discipline" reasoning above.
- *No check at all; document the risk only in migration docs*. Rejected — this is exactly the failure mode the revision brief flagged as unacceptable; documentation alone does not stop an operator from missing one step during a multi-step migration.

## 6. Migration tooling scope

**Decision**: `Makefile`'s `gen-admin-password` target is removed and replaced by `hash-static-user-password` — a thin wrapper around the already-existing `gitctl hash-password` subcommand (unchanged; no new hashing tool, consistent with the first draft's Decision 3) that prints the bcrypt hash **and** an explicit reminder of the two manual edits still required: adding `{username, password_hash}` to `users.yaml`, and adding a matching `role_bindings` entry to `policy.yaml`. It does **not** attempt to auto-write either YAML file.

**Rationale**: `gen-admin-password`'s old job — writing a bcrypt hash into a single, well-known `.env` key via `sed` — is a safe, mechanical single-key replace. Inserting a new entry into a YAML *list* (`users.yaml`'s `users:` array) or a YAML *map* (`policy.yaml`'s `role_bindings:` map) without a YAML-aware tool risks corrupting either file with naive shell text manipulation, and this spec's own Assumptions (config-file-driven only, no self-registration/management API for v1, carried over unchanged from the first draft) already establish that hand-editing these files is the intended v1 operator experience — `rbac-local`'s own `role_bindings`/`roles` entries are hand-edited today with no tooling at all. Printing the hash plus a clear, copy-pasteable reminder is the smallest addition consistent with that existing convention.

**Alternatives considered**:
- *A `gitctl users add` subcommand that safely rewrites `users.yaml` via a YAML library*. Considered — this would be a reasonable future enhancement once a real operator workflow demands it, but is explicitly deferred: it would need to solve upsert-by-username semantics, preserve comments/formatting, and decide how to handle `policy.yaml`'s `role_bindings` symmetrically — meaningfully more scope than this spec's v1, file-driven-and-hand-edited convention calls for.
- *Auto-write both files from a single `make migrate-static-admin-to-static-users` target*. Rejected for the same reason Decision 4 rejected a runtime auto-fallback: an automated cross-file edit (touching both an AuthN provider's user list and an AuthZ provider's policy file) is exactly the kind of implicit, config-file-invisible action this spec is designed to eliminate. `bootstrap-token`/`bootstrap-namespace`/`bootstrap-repository`'s existing `ADMIN_USERNAME`/`ADMIN_PASSWORD` Makefile variables are kept unchanged in name (they still describe "the identity used to bootstrap," which remains an accurate, if now role-based rather than hardcoded, description) — only their inline hint text is updated to reference `users.yaml`/`hash-static-user-password` instead of `gen-admin-password`/`GITSTORE_AUTH__ADMIN__PASSWORD_HASH`.

## 8. `ChainedAuthN.IssueSessionFor` — dropped

**Decision**: The first draft's proposed additive `ChainedAuthN.IssueSessionFor(ctx, principal)` registry method is **not** added in this revision.

**Rationale**: That method existed to solve one specific problem: `ChainedAuthN.IssueSession(ctx, subject)`'s "first provider in the chain that supports it wins" resolution strategy becomes ambiguous, and unsafe, only when *more than one* chained provider both (a) implements `IssueSession` successfully for arbitrary subjects and (b) is reachable in the same chain. With `static-admin` removed, `static-users` is the only provider in any currently-designed chain that mints locally-signed session tokens at all:
- `anonymous.IssueSession` returns `ErrNotSupported` (unchanged, confirmed by reading `anonymous/provider.go`).
- The not-yet-implemented `oidc-jwt` provider is documented (`020-pluggable_auth_architecture.md` §2b, and confirmed by the existing `RefreshToken` mutation's own doc comment in §3d: *"oidc-jwt: returns ErrNotSupported (use IdP refresh endpoint directly)"*) to return `ErrNotSupported` for both `RefreshSession` and — by the same "the IdP owns token issuance, not GitStore" design principle — `IssueSession`, since an OIDC-authenticated principal's token comes from the external IdP's own token endpoint, never from GitStore minting one locally.

With no second `IssueSession`-capable provider in any currently-designed chain, `ChainedAuthN.IssueSession`'s existing "first supporter wins" behavior is unambiguous and correct as-is — there is nothing for `IssueSessionFor` to disambiguate. Adding it now would be exactly the kind of speculative, no-current-consumer complexity Principle VII (Simplicity & YAGNI) already rejects elsewhere in this spec's own reasoning (see the first draft's Decision 6, UserDir sufficiency, for the same pattern of argument). If a future spec adds a second local, token-minting AuthN provider to the chain, that spec is the right place to revisit this — not a change made speculatively here.

**Alternatives considered**: None beyond re-confirming the original problem statement no longer applies — this is a verification finding (the fix for a problem that no longer exists once its cause is removed), not a design choice with live alternatives.

## 9. `rbac-local` sufficiency — re-confirmed, still holds

**Decision**: Unchanged from the first draft. `rbac-local` requires zero source changes. `Policy.RoleBindings map[string][]string` and `RBACLocalProvider.Authorize`'s subject-keyed merge step operate on an arbitrary subject string with no assumption tying it to any particular AuthN provider — confirmed again by re-reading `provider.go`/`policy.go` in full during this revision. Removing `static-admin` does not change this finding at all; if anything it strengthens the case, since `rbac-local` is now the *only* place any role (including "admin") is ever granted, exactly as Decision 2 above describes.

## 10. UserDir — now implemented by `static-users`, read-only

**Decision**: `static-users` implements `UserDirProvider` (`GetBySubject`, `ListGroups`, `SearchUsers`) in addition to `AuthNProvider`, backed by the same `users.yaml` loaded state, extended with two new optional fields per entry: `display_name` and `email`. `UpsertProfile`/`Deactivate` (the write half of the interface) remain `ErrNotSupported` — consistent with this spec's unchanged Assumption that user management stays config-file-driven, hand-edited, with no mutation API in v1.

**Rationale for reversing the first draft's "no change needed" conclusion**: the first draft's Decision 6 was correct on its own terms — with `static-admin` in place and no live consumer of `registry.UserDir()`, there was no reason to build a UserDir implementation with no data to serve and no caller asking for it. Both premises changed: (a) `static-admin` had exactly one identity with no metadata worth exposing; `static-users` now has an arbitrary number of named identities, and "give this metadata a real home" is now a real, non-speculative need rather than a hypothetical one; (b) this revision was explicitly asked to check whether anything *should* consume it. That check (Decision 11 below) found the `createdBy`/`updatedBy` fields on `Repository`/`Namespace` — but concluded, with reasoning, that wiring UserDir into them now would be premature. The UserDir implementation itself, though, is worth shipping regardless of whether anything consumes it yet, for a narrower reason than "a consumer exists": it is the only place `users.yaml`'s optional `display_name`/`email` fields — which an operator may reasonably want to record once they're naming multiple real people instead of one shared "admin" credential — have any way to be read back out. Recording data nothing can read is arguably not worth it either, though, which is why `GetBySubject`/`SearchUsers` are implemented as real, working, tested methods rather than stubs: they are the mechanism by which that data becomes usable *if and when* a future consumer (Decision 11) is added, at zero additional cost beyond what this spec already ships for AuthN.

**Read-method semantics** (design detail, not yet a live-consumer requirement):
- `GetBySubject(ctx, subject)`: returns a populated `UserProfile` for a known username; returns a distinguishable "not found" error (a new `staticusers.ErrUserNotFound` sentinel, not `auth.ErrNotSupported`) for an unknown one — `ErrNotSupported` per the interface's own doc comment means "this provider cannot perform this kind of operation at all," which is not true here; the operation is fully supported, the subject simply doesn't exist.
- `ListGroups(ctx, subject)`: returns an empty slice, nil error for any known subject (the schema has no `groups` field — "zero groups" is a correct, supported answer, not an unsupported operation) and the same "not found" sentinel for an unknown one.
- `SearchUsers(ctx, query, limit)`: a simple case-insensitive substring match over `username`/`display_name`/`email`, capped at `limit` — sufficient for the "handful of named local accounts" scale this whole feature targets (spec.md Assumptions, unchanged: "tens, not thousands").

**Alternatives considered**:
- *Implement UserDir as a stub returning `ErrNotSupported` for everything, matching `userdirnone`*. Rejected — this would make `display_name`/`email` write-only-forever fields with no way to read them back, which is a worse position than not having the fields at all; if they're worth adding to the schema, they're worth being able to read.
- *Leave UserDir as `none` and drop `display_name`/`email` from the schema entirely, revisiting only if a future spec needs them*. Rejected because the coordinator's direction was explicit: implement UserDir now specifically so this metadata "has a real home" — this alternative would not satisfy that direction, and the marginal cost of the read-only methods is small (no new dependency, no new file, same load path already built for AuthN).

## 11. Should anything consume UserDir yet? — investigated, answer is "not in this spec"

**Finding**: `Repository.createdBy`/`Repository.updatedBy` and `Namespace.createdBy`/`Namespace.updatedBy` (`shared/schemas/repository.graphqls`, `shared/schemas/namespace.graphqls`) are plain `String!` fields, populated directly from `Principal.Subject` (the bare username) at write time — confirmed by schema inspection; there is no `Author`/`User`-typed field anywhere that could resolve `registry.UserDir().GetBySubject(...)` to surface a display name. There is also a dead, never-populated `type User { username, isAdmin }` GraphQL type (`shared/schemas/auth.graphqls`) that is not returned by `login` (`LoginPayload` returns only `token`) or by any query.

**Decision**: Do not change `createdBy`/`updatedBy` from `String!` to a richer, UserDir-resolved type in this spec, and do not wire `registry.UserDir()` into any resolver here.

**Rationale**: Changing `createdBy: String!` to, say, `createdBy: Author!` (a new type resolving through `UserDir().GetBySubject`) is a GraphQL schema change to two existing, public, non-nullable fields on two existing types (`Repository`, `Namespace`) — a materially larger, separate design decision (new type, resolver plumbing, deprecation path for the old `String!` shape per Constitution Principle III's "GraphQL changes MUST prefer additive evolution and deprecation before removal") than "add a UserDir provider." It is also not needed to satisfy this spec's own goals: User Stories 1–4 (multi-user AuthN, `role_bindings` end-to-end, migration safety, backdoor retirement) are all fully satisfiable without any GraphQL schema change at all — this spec, like its first draft, ships zero schema changes. Building the resolver wiring now, with no request driving its shape, risks guessing wrong about whether `createdBy` should become an added *sibling* field (e.g., a new optional `createdByProfile: UserProfile` alongside the unchanged `createdBy: String!`) or a breaking replacement — a decision better made by whichever future spec actually needs richer author display (e.g., an admin console feature), informed by that feature's real requirements.

**What this spec does instead**: ships the UserDir implementation (Decision 10) so that future work has a real, working, tested provider to wire in, and records this investigation here so that future spec does not need to re-derive "does anything consume this today" from scratch — the answer, precisely, is no, and the most likely first consumer, if one is ever added, is `createdBy`/`updatedBy` display enrichment via a new, additive field.

## 12. Config-validation bug: unconditionally-required auth secrets, found while touching this exact surface

**Finding**: `gitstore-api/internal/config/config.go`'s `validateConfig` runs a single `validate.Struct(cfg)` pass over the *entire* `Config` tree via `go-playground/validator/v10`'s struct tags, with no awareness of `cfg.Auth.AuthN.Chain`'s contents. Three fields carry `validate:"required"` inside `AuthConfig`'s substructures, enumerated exhaustively by reading every `validate:` tag in the file:

| Field (struct tag) | Config key | Today's behavior | Actually tied to |
|---|---|---|---|
| `JWTConfig.Secret` | `auth.jwt.secret` | **Unconditionally required** — server refuses to start if empty, regardless of `auth.authn.chain` contents | `static-admin`'s (now `static-users`') own session-signing secret only — confirmed by `grep -rn "cfg.Auth.JWT\|Auth.JWT\b" gitstore-api --include="*.go"`, excluding tests: the only non-logging consumer is `staticadmin.New` (now `staticusers.New`). |
| `UserConfig.Username` / `UserConfig.Password` | `auth.admin.username` / `auth.admin.password_hash` | **Unconditionally required** — same as above | `static-admin`'s single credential. Moot after removal — the whole `Admin UserConfig` field is deleted, not just its tags. |
| `GrpcAuthConfig.HmacSecret` | `auth.grpc.hmac_secret` | **Unconditionally required** | The API↔git-service gRPC inter-service HMAC trust (`gitstore-api/internal/gitclient/auth.go`'s `hmacCreds`) — used on every gRPC call the API makes to git-service, completely independent of which end-user-facing AuthN provider(s) are chained in. This is the field a prior direct-experience report suspected but couldn't name; confirmed here by reading the field's sole consumer. |

**Decision**: Fix the first two (both tied to AuthN provider selection); explicitly rule the third **out of scope** — it is correctly required unconditionally, since git-service connectivity is not optional infrastructure gated by AuthN chain choice, it's used regardless.

The fix: remove `validate:"required"` from `JWTConfig.Secret`'s struct tag (the `UserConfig`/`Admin` fields disappear entirely as part of removing `static-admin`, so their tags disappear with them — no separate action needed). Add a new, explicit `validateAuthChainConfig(cfg *Config) error` function, called from `validateConfig` alongside the existing `validateDatastoreConfig`/`validateLogFormat` calls (the same file already establishes this "generic struct validation, then explicit semantic checks" two-phase pattern — this is not a new pattern, it's reusing the one already there), that requires `cfg.Auth.JWT.Secret` to be non-empty **only if** `"static-users"` appears in `cfg.Auth.AuthN.Chain`.

**Rationale**: `validator/v10`'s built-in `required_if` tag only supports equality comparisons against a sibling/parent field's *value* — it has no "slice contains this element" predicate, so "required only if `static-users` is one of possibly several entries in `auth.authn.chain`" cannot be expressed as a struct tag at all; it requires an imperative check, which is exactly the shape `validateDatastoreConfig`/`validateLogFormat` already use for their own non-struct-tag-expressible rules. Today's unconditional requirement is a genuine startup-ergonomics bug independent of this spec's provider swap — an operator who only wants, say, `anonymous`-only or (once implemented) `oidc-jwt`-only authentication is forced to set a JWT secret their configuration will never use, with no way to omit it. Fixing it now, while this exact validation surface is already being touched for the provider swap, avoids reintroducing the same mistake under a new name: `static-users`' own new config key (`auth.staticusers.users_file`, see `data-model.md`) is deliberately given **no** `validate:"required"` struct tag either — its file is loaded, and thus validated, only inside `buildProviderRegistry`'s `case "static-users":`, which already only runs when that provider is actually chained in. That is the correct pattern this fix generalizes from one already-correct example (the new key) to one previously-incorrect one (the pre-existing JWT secret key).

**Alternatives considered**:
- *Leave `auth.jwt.secret` unconditionally required; document it as a known limitation*. Rejected — this is the exact bug being reported from direct operator experience; documenting a startup failure instead of fixing it, while already touching this file for an unrelated-but-adjacent reason, is not a reasonable trade-off.
- *Make `auth.grpc.hmac_secret` conditional too, "for consistency"*. Rejected — confirmed its requirement is unconditionally correct; making it conditional on AuthN provider choice would be a functional regression (a git-service-connectivity secret must not depend on which end-user AuthN providers happen to be configured), not a consistency improvement.

## 13. Relationship to spec 059 (optional OIDC provider) — unchanged

**Decision**: Unchanged from the first draft. Purely complementary — no shared code, no shared config surface, no design dependency in either direction. Removing `static-admin` does not change this: spec 059's Hydra+Kratos stack and the not-yet-implemented `oidc-jwt` provider it targets are untouched by this revision.
