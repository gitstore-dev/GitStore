# Research: Product Watch Transport for CategoryTaxonomy Count Reconciliation

## R1: How `gitstore-controller-manager` observes Product changes

**Decision**: Add a second `listwatch.Runner[Product]` (a new, small `Product` cache entity type, not the existing `categorytaxonomy.CategoryTaxonomy` type) driven by a new `ProductListWatcher` against the existing `products` query and a new **dedicated** `watchProducts(namespace: String, selector: LabelSelectorInput, resourceVersion: String): ProductWatchEvent!` GraphQL subscription, added to `shared/schemas/product.graphqls` alongside `Product`'s existing `Query`/`Mutation` extensions — mirroring `watchCategories`/`CategoryWatchEvent` field-for-field, not the generic `watchResources(kind: String!, ...)` path. This `Runner[Product]` is registered and run exactly like the existing `CategoryTaxonomy` runner (own cache, own checkpoint file, own list-then-watch/resume loop), but **no `Reconciler` is registered for `"Product"`** in the `Manager` — the Product cache's `OnAdd`/`OnUpdate`/`OnDelete` handlers only translate a Product change into `CategoryTaxonomy` `WorkItemKey` enqueues via the already-registered `CategoryTaxonomy` reconciler, mirroring the existing category→parent-category enqueue pattern already in `cmd/controller/main.go`'s `registerCategoryTaxonomy`.

**Rationale**: `Product` is a core kind — it already has its own compile-time-typed `Product`/`ProductSpec` GraphQL types and its own `Query`/`Mutation` schema extensions (`shared/schemas/product.graphqls`), exactly like `CategoryTaxonomy` did before spec 040 gave it `watchCategories`. Spec 040 R7 is explicit that the generic, JSON-boxed `watchResources(kind: String!, ...)` path exists specifically for CRD kinds with no schema-time-known shape ("gqlgen generates Go types from the schema at build time; a truly generic 'any resource' GraphQL type cannot carry compile-time-typed fields for kinds that don't exist in the schema yet") — and spec 040 R1 already established the precedent that every core kind gets its own dedicated, strongly-typed watch field (`watchCategories`/`CategoryWatchEvent`) rather than routing through the generic path, precisely so core-kind consumers get full type safety. Using the generic path for Product would mean unmarshaling a `JSON`-boxed `object` field on every event, in both `gitstore-controller-manager`'s new `ProductListWatcher` and any future core consumer of Product watch events, for no reason — Product's shape is fully known at schema-compile time today and forever, since it isn't a CRD. A dedicated `watchProducts` field costs one new schema field and one new generated Go type (following an established, mechanical pattern with an existing precedent to copy), and pays for itself immediately by giving `ProductListWatcher.Watch` the same type-safe unmarshal `CategoryTaxonomyListWatcher.Watch` already enjoys. The rest of the mechanism (`Runner[T]`, `Cache[T]`, `Manager.Enqueue`) is unchanged from the original decision and still fully reused.

**Alternatives considered**:
- *Route Product events through the existing generic `watchResources(kind: "Product")`*: rejected — this was the original decision here but conflates "no new schema-visible mutation contract" (still true) with "must reuse the JSON-boxed generic path" (not required, and wrong for a core kind per spec 040 R7's own stated purpose for that path). `watchResources` is reserved for kinds that don't have a compile-time GraphQL type — Product does, so using the JSON-boxed path would be strictly worse type safety for no simplicity gain: the schema change (one new `Subscription` field, one new event type) is exactly as small as adding `watchCategories` was, and `CategoryWatchEvent` is the direct precedent to copy.
- *Register `"Product"` as its own reconciled kind with a real (no-op) `Reconciler`, purely so its cache/queue gets the existing health metrics and quarantine machinery*: rejected — a `Reconciler` that does nothing but exists to satisfy `Manager.Register` is a speculative abstraction (Simplicity/YAGNI); the cache's `OnAdd`/`OnUpdate`/`OnDelete` handlers are sufficient to drive the actual side effect (enqueuing `CategoryTaxonomy` work), and `CategoryTaxonomy`'s own queue-depth/stall metrics already reflect the work this feature adds to that queue, which is the operationally relevant signal.
- *Skip the `Runner[Product]`/cache entirely and instead have the `gitstore-api` event carry enough information to enqueue directly from a raw subscription callback, without a Product-side cache at all*: rejected — this would need its own hand-rolled resume/checkpoint/reconnect logic to satisfy FR-006/FR-007, duplicating `Runner[T]`'s existing, already-tested implementation instead of reusing it. The cache itself is also cheap (Product's cached fields are minimal — see R2) and its `List()` on bootstrap is what correctly seeds "categories affected by products that already existed before this process started," which a raw event-only approach would miss.

## R2: What the Product cache entity needs to carry

**Decision**: The new `Product` cache entity type (distinct from any `gitstore-api`-side `datastore.Product`) carries only: `UID`, `Namespace`, `Name`, `ResourceVersion`, and `CategoryRefName string` (empty string when the product has no category reference). `OnUpdate`'s handler compares `old.CategoryRefName` vs `current.CategoryRefName`: if unchanged, no enqueue is needed for the category dimension (categoryRef-unrelated product edits — e.g. a spec/body change with the same category — must not cause a spurious `CategoryTaxonomy` reconcile); if changed, both are enqueued (when non-empty). `OnAdd` enqueues `current.CategoryRefName` (when non-empty); `OnDelete` enqueues the deleted product's last-known `CategoryRefName` (when non-empty).

**Rationale**: This mirrors `categorytaxonomy.CategoryTaxonomy`'s cache entity, which similarly carries only the fields its own `OnAdd`/`OnUpdate`/`OnDelete`-driven parent-enqueue logic needs (`ParentRefName`), not the full product resource. Comparing old vs. new `CategoryRefName` inside `OnUpdate` is the mechanism that satisfies FR-004 ("re-evaluate only the category actually affected") for the update case — a product's non-category fields (spec/body, metadata) changing must not trigger an unrelated `CategoryTaxonomy` reconcile, since `productCount` does not depend on them.

**Alternatives considered**:
- *Cache the full Product resource (spec, body, etc.)*: rejected — nothing downstream of this feature needs any Product field beyond identity and category reference; caching more is unused memory and surface area with no behavioral benefit (Simplicity/YAGNI).
- *Skip the old/new comparison and always enqueue on every Product update regardless of whether `categoryRef` changed*: rejected — this would violate FR-004 and SC-005 (no reconciliation activity for unrelated changes) whenever a product's non-category fields change, which is expected to be the common case for ordinary catalog edits.

## R3: How `gitstore-api` decides when to publish a Product event

**Decision**: Add a `publishProductEvent(evType eventbus.EventType, p *datastore.Product)` helper in `cataloggrpc/server.go`, mirroring the existing `publishCategoryTaxonomyEvent`, and call it from three places: (1) in `admitProduct`, after a successful `s.store.CreateProduct` (event type `Added`); (2) in `admitProduct`, after a successful update — but **only when `existing.CategoryRef` (parsed from `existing.Spec`) differs from the incoming `resource.Spec.CategoryRef`**, not on every update — since `admitProduct` already computes `changedSpecBody`/`changedMetadata`/`changedProvenance` and short-circuits entirely when none of those changed; a categoryRef-only change is a `changedSpecBody` case (categoryRef lives inside `Spec`), so the existing short-circuit already prevents an event on a true no-op, and this feature adds the additional category-ref-diff check so a spec change that is *not* a categoryRef change (e.g. a price/description edit) still writes the product but does not publish an event that would cause a spurious `CategoryTaxonomy` reconcile; (3) in `deleteResource`'s existing `*datastore.Product` case, alongside the current `*datastore.CategoryTaxonomy` `Publish` call, using the deleted product's last-known `categoryRef` (event type `Deleted`).

**Rationale**: This follows the exact existing precedent (`publishCategoryTaxonomyEvent`'s three call sites: create at line ~1346, update at line ~1390, delete via `deleteResource` at line ~691) and the exact existing gating precedent (`admitProduct`'s current `if !changedSpecBody && !changedMetadata && !changedProvenance { return }` no-op short-circuit) — no new no-op-detection mechanism is introduced. Restricting the update-path publish to only categoryRef-changed cases (rather than "any update") is what satisfies FR-004/SC-005 at the source, so `gitstore-controller-manager`'s R2 comparison is a defensive-in-depth double-check, not the only enforcement point — belt-and-suspenders against either side's logic drifting, matching the spec's explicit edge case about unrelated changes not triggering reconciliation.

**Alternatives considered**:
- *Publish an event on every Product create/update/delete unconditionally, and rely solely on the controller-manager's OnUpdate diff (R2) to filter*: rejected as the sole mechanism — it would still generate eventbus traffic and controller-manager cache churn for every unrelated product edit, adding load with no purpose. Filtering at the source (R3) plus defensively at the consumer (R2) is cheap and keeps both layers independently correct.
- *Add a brand-new `EventType` (e.g. `CategoryRefChanged`) distinct from the existing `Added`/`Modified`/`Deleted`*: rejected — the existing three-value `EventType` enum is sufficient; the controller-manager already needs to inspect the resource's `categoryRef` field regardless of event type to know what changed (R2's old-vs-new comparison happens on `Modified` events already), so a new enum value adds a case without adding information the payload doesn't already carry via `Object`.

## R4: Extracting `categoryRef` from the `watchProducts` payload

**Decision**: Following R1's dedicated-subscription decision, add a new `ProductWatchEvent` GraphQL type (mirroring `CategoryWatchEvent` field-for-field) carrying `type: WatchEventType!`, `namespace: String`, `name: String!`, `resourceVersion: String!`, and a strongly-typed `product: Product` (null for `DELETED`/`BOOKMARK`, matching `CategoryWatchEvent.category`'s existing convention). A new `subscriptionResolver.WatchProducts` resolver (mirroring `WatchCategories` exactly) subscribes to `r.eventBus.Subscribe("Product", rv)` and maps each `eventbus.Event` to a `*model.ProductWatchEvent`, setting `Product` from `ev.Object.(*datastore.Product)` via the same converter pattern `WatchCategories` already uses for `Category`. The new `ProductListWatcher.Watch()` in `gitstore-controller-manager` then reads the already-typed `product.spec.categoryRef.name` field directly from the GraphQL response — no JSON-boxed payload, no client-side unmarshaling of an opaque blob. `categoryRef` already exists end-to-end today (confirmed present in `gitstore-api/internal/catalog/product.go`'s `CategoryRef *ObjectReference` and the generated `ProductSpec.categoryRef` GraphQL field) — this decision only adds the new watch-envelope type, not a new underlying field.

**Rationale**: This follows directly from R1: since Product gets its own dedicated, compile-time-typed subscription (not the generic JSON-boxed `watchResources` path), the payload it carries should be the existing typed `Product` GraphQL type, exactly as `CategoryWatchEvent.category: Category` already does — consistency with the one existing precedent, not a new convention. This also means `ProductListWatcher` needs no JSON-unmarshal-into-untyped-map step at all (unlike the original `watchResources`-based design), simplifying `ProductListWatcher.Watch` relative to the generic path.

**Alternatives considered**:
- *JSON-box the payload as `object: JSON` on a new `ProductWatchEvent`, matching the generic `WatchEvent.object` shape instead of `CategoryWatchEvent.category`*: rejected — there is no reason to sacrifice type safety on a dedicated, core-kind-specific event type; `JSON`-boxing is the compromise `WatchEvent` makes specifically because it must remain generic across unknown future CRD shapes, a constraint `ProductWatchEvent` does not have.

## R5: Collapsing redundant enqueues during a burst (Edge Cases, SC-006)

**Decision**: Rely entirely on the existing per-kind work queue's dedup behavior already used by `CategoryTaxonomy`'s own category→parent-category enqueue path (`manager.Manager.Enqueue` → `ks.q.Enqueue`) — no new debouncing/coalescing mechanism is introduced. The existing queue is keyed by `WorkItemKey` (kind+namespace+name), so N enqueues of the same `CategoryTaxonomy` key within a burst before that key is dequeued and processed already collapse to at most one pending item for that key (this is the same property that already makes the existing category→parent-category propagation safe under a bulk category push).

**Rationale**: The spec's Edge Cases explicitly call out "a burst of many product changes affecting the same category must converge without one-reconciliation-per-change cost" — this is already true today for the analogous category-hierarchy case and requires no new code; verifying it (via a contract/integration test using the new Product trigger) is the correct scope for this feature, not building a second coalescing layer.

**Alternatives considered**:
- *Add a debounce/coalescing window in front of `mgr.Enqueue` specific to Product-driven enqueues*: rejected — this would be a second, parallel coalescing mechanism alongside the queue's existing one, adding complexity without addressing a gap (the existing mechanism already collapses same-key enqueues); only justified if testing reveals the existing queue does not, in fact, dedup as expected for this new call path, which Phase 2 tasks should verify before assuming.

## R6: Restart-survival mechanism (FR-006, US4)

**Decision**: Reuse `Runner[T]`'s existing checkpoint/resume loop with a related-replay extension — the new observer-only `Runner[Product]` gets its own checkpoint file (via the same `checkpoint.FilesystemStore` already used for `CategoryTaxonomy`, keyed by kind), does not retain Product work keys, and persists affected `CategoryTaxonomy` keys until that kind reports successful reconciliation. On restart, the Product snapshot restores current categories while the related replay set restores former categories for deletions/reassignments; an expired cursor triggers the existing full re-`List()` recovery. Because `CategoryTaxonomy`'s own `Reconcile` already suppresses no-op status writes (`patch.IsNoOp`, spec 039 FR-013), replaying an already-correct category after restart is safe.

**Rationale**: This is the same restart-survival guarantee spec 036/040/039 already provide for category-driven reconciliation, extended to a second watched kind by construction rather than by new logic — `Runner[T]` was built generically for exactly this reuse. `IsNoOp` (already shipped) is what makes "at-least-once delivery is safe to replay" true without new dedup-on-replay logic.

**Alternatives considered**:
- *Share a single checkpoint file/cursor across both the `CategoryTaxonomy` and `Product` runners*: rejected — `Runner[T]`'s checkpoint contract is per-kind (one `Store` interaction per `Kind` string), and the two kinds have independent, unrelated `resourceVersion` sequences on the `gitstore-api` side (each `eventbus` kind buffer is independent); conflating them would require new code to disentangle two kinds' cursors from one file, achieving nothing the existing per-kind-file design doesn't already provide correctly.
