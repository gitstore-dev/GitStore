# Feature Specification: Product Deletion Safety via ProductVariant OwnerReferences

**Feature Branch**: `055-product-deletion-safety`
**Created**: 2026-08-20
**Status**: Draft
**Input**: User description: "Product Deletion Safety: Block Delete While ProductVariants Exist (GH#377). Reject Product deletion when at least one ProductVariant still references it via the required spec.productRef, using the same metadata.ownerReferences + blockOwnerDeletion mechanism adopted for CategoryTaxonomy (#243, spec 052) — not a spec.productRef.name scan. In scope: ProductVariant admission writes a blockOwnerDeletion: true ownerReferences entry on the variant pointing at its Product; Product deletion (git push and GraphQL) queries the indexed ownerReferences lookup and rejects when any blocking entry exists; foreground-deletion finalizer + Terminating condition on eligible Product deletion; re-evaluation of the blocking-dependent query on every reconcile of a terminating Product. Out of scope: cross-namespace categoryRef/productRef validation, ProductVariant's own deletion semantics beyond its ownerReferences entry, pricing/inventory/reservation resources, CategoryTaxonomy's own deletion semantics (spec 052), and any decouple/orphan path for this relationship (none exists — a ProductVariant cannot exist without a Product, so this is pure block)."

## Clarifications

### Session 2026-08-20

- Q: GH#243's precedent (spec 052, CategoryTaxonomy) split dependents into "blocks" (children) and "decouples" (assigned products). Does this spec need the same split for ProductVariant → Product? → A: No — this relationship is pure block, with no decouple side. `ProductVariant.spec.productRef` is required (ADR-0005, spec 024); an orphan variant with no product is not a supported state, unlike a `Product` with no `spec.categoryRef` (which is already a normal "uncategorized" state — the exact asymmetry that let spec 052 split its two dependent types). Every `ProductVariant` found by the blocking-dependent lookup unconditionally blocks `Product` deletion; there is no `blockOwnerDeletion: false` counterpart for this relationship, and no status field on `Product` is repurposed the way `CategoryResolved` was repurposed on `Product` by spec 052.
- Q: Should a newly created `ProductVariant` be rejected at admission if its `spec.productRef` names a `Product` that is already `Terminating` — mirroring spec 052's rejection of a new `categoryRef` against a `Terminating` `CategoryTaxonomy` (FR-014) and spec 046's rejection of new resources under a `Terminating` `Namespace`? → A: No — the opposite of that precedent applies here, per GH#377's own acceptance criteria ("A ProductVariant created after a deletion request was accepted still withholds final removal"). The issue explicitly requires this exact race to be handled by continuing to withhold removal, not by rejecting the new variant at admission. This is intentional, not an oversight: rejecting the new variant would gain nothing here, because (unlike a `categoryRef`, which has a safe "leave it unset" alternative) a `ProductVariant` cannot be authored at all without *some* `productRef` — if the named product is mid-deletion, the author's only alternative is to wait for it to fully disappear, at which point the variant would fail for the unrelated reason that the product no longer exists. Admitting the variant and letting it correctly withhold the in-flight deletion is the behavior the issue asks for, and is consistent with "pure block": a live blocking dependent is a live blocking dependent, regardless of when it appeared relative to the deletion request.
- Q: `ProductResolved` on `ProductVariant` is resolved synchronously inside git-push admission today (`gitstore-api/internal/cataloggrpc/server.go`, `admitProductVariant`), not asynchronously by a controller — unlike `CategoryTaxonomy`'s `ParentResolved`, which spec 039's controller reconciler resolves asynchronously. Should this spec's `ownerReferences` write follow the synchronous admission-time pattern already used for `ProductResolved`, or introduce a new asynchronous controller-driven resolution path for this one write? → A: Follow the existing synchronous pattern. The `blockOwnerDeletion: true` `ownerReferences` entry on a `ProductVariant` is written at the same point, and by the same mechanism, that already computes `ProductResolved=True` today (at admission, whether the `Product` already existed or was co-admitted earlier in the same push batch). Introducing a separate asynchronous resolution path for only this one field, when no `Product`- or `ProductVariant`-owning controller reconciler exists today to drive it, would add an inconsistent second resolution mechanism for the exact same underlying reference this spec has no reason to resolve differently.
- Q: The drain/re-check loop for a `Terminating` `Product` (re-evaluating the blocking-dependent query on every reconcile) needs a reconciliation loop to run in, but `gitstore-controller-manager/internal/` has no `product` or `productvariant` package today (confirmed: only `categorytaxonomy/` and `namespace/` reconciler packages exist; the only Product-adjacent logic lives in `categorytaxonomy/products.go`, which only computes category product-counts and owns no Product lifecycle state). What does this spec's drain step hook into? → A: A new, minimal `gitstore-controller-manager/internal/product` reconciler package, following the exact precedent set by spec 046 when no `Namespace` reconciler existed yet (`gitstore-controller-manager/internal/namespace/reconciler.go`, with its own `ForegroundDeletionFinalizer` constant and `DeletionClient`). This new package needs its own watcher/cache wiring (mirroring `namespace`'s and `categorytaxonomy`'s each having their own), but reuses the already-working, kind-agnostic watch/eventbus machinery as-is — `"Product"` is already a valid `kind` flowing through `gitstore-api/internal/eventbus` (confirmed in production code paths via spec 042's product-category-count feature), so no new subscription-protocol or eventbus infrastructure is needed, only a new consumer of it.
- Q: Does a working `deleteProduct` GraphQL mutation already exist for this spec to add a precondition check to (the way spec 052 found `DeleteCategory` existing as an unconditional-error stub)? → A: No — confirmed by direct read of `shared/schemas/product.graphqls` (no `extend type Mutation` block at all) and `gitstore-api/internal/graph/resolver/product.resolvers.go` (no Delete/Create/Update resolver of any kind). This is a more minimal starting point than CategoryTaxonomy's: there is no schema field and no stub resolver to fix. This spec's GraphQL-path requirement (FR-004) is new schema-plus-resolver work — adding a `deleteProduct` mutation and its input/payload types — not a bug fix to existing wiring. `createProduct`/`updateProduct` remain git-push-only and are explicitly out of scope; only the minimal `deleteProduct` mutation needed to enforce this spec's precondition check is added.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Deleting a product with live variants is rejected, not silently applied (Priority: P1)

Today, deleting a `Product` file in a git push is admitted unconditionally: `deleteResource` in the admission pipeline (`gitstore-api/internal/cataloggrpc/server.go`) hard-deletes the record with no check for `ProductVariant` records whose `spec.productRef` still points at it. An author who deletes a product file while its variants still exist gets no warning — the product silently disappears while its variants are left referencing a product name that no longer resolves, even though every one of those variants is defined (ADR-0005) to require a valid product and has no supported existence without one.

**Why this priority**: This is the core correctness gap the issue exists to close. Without it, the variant-first sellable contract (GH#143, ADR-0005) is undermined at its foundation — a variant is supposed to be unable to exist without its product, yet today a product can vanish out from under live variants with no protection at all.

**Independent Test**: Can be fully tested by pushing a deletion of a product that has at least one `ProductVariant` whose `spec.productRef` points at it, and confirming the delete is rejected and the product record still exists afterward, with the variant's own state unchanged — all without needing the GraphQL delete path or controller drain behavior to exist yet.

**Acceptance Scenarios**:

1. **Given** a product with at least one `ProductVariant` whose `spec.productRef` points at it, **When** a git push deletes the product's manifest file, **Then** the deletion is rejected, the product record is unchanged in the datastore, and the rejection is distinguishable from a successful delete.
2. **Given** a product with no `ProductVariant` referencing it, **When** a git push deletes its manifest file, **Then** the deletion proceeds.
3. **Given** a product whose only variant was itself already deleted in an earlier, already-admitted push, **When** the (now variant-free) product's manifest is deleted, **Then** the deletion proceeds.

---

### User Story 2 - The same deletion safety applies to the GraphQL API, not only git push (Priority: P1)

An operator or integration using the GraphQL API needs a working way to request product deletion without constructing a git commit by hand, and that path must enforce the exact same rule as the git-push path. Today there is no `deleteProduct` GraphQL mutation at all — no schema field, no resolver, not even a stub — so this is new capability, not a fix to an existing gap.

**Why this priority**: Equal priority to User Story 1 — a safety rule that only one of two entry points enforces is not a safety rule, and GraphQL callers are a first-class way this system is used, per the delegation pattern already implemented for other resource kinds' mutations.

**Independent Test**: Can be fully tested by calling the new GraphQL `deleteProduct` mutation against a product with live variants and confirming it is rejected with the same reason as the git-push path, and calling it against a variant-free product and confirming deletion proceeds end-to-end.

**Acceptance Scenarios**:

1. **Given** a product with at least one live `ProductVariant`, **When** the `deleteProduct` mutation is called, **Then** it is rejected identifying existing variants as the blocking reason, and the product is unchanged.
2. **Given** a variant-free product, **When** the `deleteProduct` mutation is called, **Then** the product is marked as being deleted (deletion marker plus foreground-deletion finalizer) and eventually removed.
3. **Given** a product already marked as being deleted, **When** the `deleteProduct` mutation is called again for the same product, **Then** it is treated as redundant with the existing in-progress deletion, not as a second, independent deletion attempt.

---

### User Story 3 - A product mid-deletion is visibly distinguishable, and its removal only happens once it is actually safe (Priority: P2)

Once a product passes its dependent check and begins deleting, the system must never destroy its record before every remaining variant is actually gone, and must expose that in-progress state so a reader (human or controller) can tell a normal product apart from one that is being torn down. This includes the case where a new variant is created against the product after its deletion was already accepted.

**Why this priority**: Lower urgency than User Stories 1-2 because it depends on those first passing (there is nothing to make visible until deletion is actually gated), but it is what makes the drain-then-remove sequence observable, trustworthy, and race-safe rather than an internal implementation detail no one can verify.

**Independent Test**: Can be fully tested by deleting an eligible product through the GraphQL mutation and observing its status expose an in-progress-deletion condition before the record disappears, then separately creating a new variant against a product already in that state and confirming removal is withheld until that variant, too, is gone.

**Acceptance Scenarios**:

1. **Given** a product that has passed its dependent check and begun deletion, **When** its status is read before removal completes, **Then** it exposes a `Terminating=True` condition distinguishing it from an active product.
2. **Given** a product mid-deletion whose variant count is zero, **When** the controller next reconciles it, **Then** the product's record is finally removed and no further reconciliation of it occurs.
3. **Given** a product that re-acquires a variant between its initial dependent check and final removal (a new `ProductVariant` is created pointing at it before drain completes), **When** the controller reconciles it, **Then** removal is withheld until that variant, too, is gone — final removal never happens while any variant still exists, regardless of when that variant was created relative to the deletion request.

---

### Edge Cases

- What happens to a `ProductVariant` while its `Product` is `Terminating`? Nothing special — under this block-until-drained model, a product's deletion is rejected/withheld for as long as any variant exists, so a variant is never actually left referencing a product that has been removed. The variant's own `ProductResolved` condition continues to correctly report `True` for as long as the product record still exists, which it always does while any variant remains.
- Can a new `ProductVariant` be created, or an existing one updated, to reference a `Product` that is already `Terminating`? Yes — deliberately, per the Clarifications above and GH#377's race-safety acceptance criterion. Admission is unchanged for this case; the new (or updated) variant's `ownerReferences` entry is written exactly as it would be against any other product, and the product's deletion continues to be withheld for as long as that variant exists.
- What happens if a product delete request races with a concurrent variant-create targeting the same product? The blocking-dependent check is re-evaluated by the controller on every reconcile of the terminating product (User Story 3, Scenario 3), so a variant created after the initial synchronous check but before final removal still blocks removal — there is no window in which removal can occur while a variant still exists.
- What happens to a `ProductVariant`'s own `metadata.ownerReferences` entry to its `Product` when the variant itself is deleted? It disappears along with the rest of the variant's record as part of the variant's own existing deletion lifecycle (ADR-0005); no separate cleanup step is needed, since the blocking-dependent lookup only ever considers variant records that still exist.
- What happens on a redundant delete request (git push deleting an already-deleted-in-flight product's file again, or a second GraphQL deletion call)? Treated as a no-op against the existing in-progress deletion — it does not restart, duplicate, or advance the deletion beyond where it already was.
- What happens to `metadata.ownerReferences` on a `Product` record itself? Unchanged by this spec — a `Product`'s own `ownerReferences` (e.g. pointing at its owning repository, or at a resolved `CategoryTaxonomy` per spec 052) are outside this spec's scope; this spec only adds the `ProductVariant → Product` entry and the query that reads it.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST write a `metadata.ownerReferences` entry — `{kind: Product, name, uid, blockOwnerDeletion: true}` — on a `ProductVariant` record pointing at its resolved product, at the same point `ProductResolved` transitions to `True` (synchronously at admission — whether the product already exists in the datastore or was co-admitted earlier in the same push batch), mirroring the trigger already used for `ProductResolved` itself.
- **FR-002**: The system MUST determine whether a `Product` has a blocking dependent by querying for any resource whose `metadata.ownerReferences` contains an entry for that product's `uid` with `blockOwnerDeletion: true` — not by scanning for `spec.productRef.name` string matches — and MUST reject a deletion request (via git push or the GraphQL mutation) when that query returns at least one result, leaving the product's record unchanged.
- **FR-003**: The system MUST provide a working GraphQL `deleteProduct` mutation (schema field, input/payload types, and resolver — none of which exist today) that performs the same `blockOwnerDeletion: true` dependent check (FR-002) synchronously and rejects the request, identifying existing variants as the blocking reason, when that check fails.
- **FR-004**: The system MUST, upon an eligible deletion request (FR-002's check passes) via either git push or the GraphQL mutation, mark the product as being deleted using a deletion marker plus a product-specific foreground-deletion finalizer, following the same `gitstore.dev/foreground-deletion` finalizer convention already established per-resource for `Namespace` (spec 046), before removing anything else.
- **FR-005**: The system MUST make a product marked as being deleted visibly distinguishable from an active product when its status is read, via a `Terminating` condition using the existing `ConditionTerminating` condition-type vocabulary (`gitstore-api/internal/catalog`, already shared across resource kinds).
- **FR-006**: The system MUST NOT hard-delete a `Product` record marked as being deleted until the `blockOwnerDeletion: true` dependent query (FR-002) returns zero results at the time of removal.
- **FR-007**: The system MUST re-evaluate the `blockOwnerDeletion: true` dependent query on every reconciliation of a product marked as being deleted, not only at the time the deletion request was first accepted, so a `ProductVariant` created after acceptance — including one created after the product entered `Terminating` (see Edge Cases) — still withholds final removal until it, too, is gone.
- **FR-008**: The system MUST treat a deletion request (via either git push or the GraphQL mutation) against a product already marked as being deleted as redundant with its existing in-progress deletion, not as a new, independently-tracked deletion attempt.
- **FR-009**: The system MUST NOT introduce a cascading, automatic deletion of a product's variants as a result of deleting that product — variants are never auto-removed as a side effect of this feature; `blockOwnerDeletion: true` only ever blocks, it never triggers a cascade.
- **FR-010**: The system MUST NOT reject, at admission, a `ProductVariant` create or update whose `spec.productRef.name` points at a `Product` already marked as being deleted (`Terminating`); such a variant is admitted normally, receives its own `blockOwnerDeletion: true` entry per FR-001, and its existence continues to withhold the product's final removal per FR-007.
- **FR-011**: The system MUST provide a reconciliation mechanism capable of performing the re-evaluation in FR-007 for `Product` resources, since no such mechanism exists for `Product` today.

### Key Entities

- **`metadata.ownerReferences` entry (ProductVariant → Product)**: A controller-managed metadata field (never git-authored) recording `{kind: Product, name, uid, blockOwnerDeletion: true}` on a `ProductVariant`, mirroring the mechanism spec 052 established for `CategoryTaxonomy`'s parent/child relationship. Unlike spec 052, this relationship has exactly one entry shape — there is no `blockOwnerDeletion: false` counterpart, because a `ProductVariant` cannot exist without a resolved `Product` (ADR-0005), so there is no safe decoupled state to fall back to.
- **Dependent lookup**: A query for "every resource with an `ownerReferences` entry for UID `X` with `blockOwnerDeletion: true`," reusing the same indexed-lookup shape spec 052 introduced for `CategoryTaxonomy`'s children. Replaces a `spec.productRef.name` string-match scan.
- **In-progress deletion (Terminating)**: The state a product enters once an eligible deletion request (zero blocking dependents) has been accepted and the foreground-deletion finalizer attached, prior to its record being finally removed. Distinguishable from an active product via a `Terminating` condition.
- **Product reconciler**: A new, minimal `gitstore-controller-manager/internal/product` reconciliation loop (none exists today) responsible only for the drain/re-check/finalizer-removal sequence in FR-007/FR-011 — it does not take on any other Product lifecycle responsibility (e.g. `categoryRef` resolution remains synchronous at admission, unaffected by this spec).

### Status condition matrix

| Condition                 | Source of truth                                  | Set by                          | Read semantics                                                                                                             |
|----------------------------|---------------------------------------------------|-----------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| `ProductResolved` (ProductVariant) | datastore `Status.conditions` (existing, synchronous admission) | admission chain            | unchanged by this spec, except that its `True` transition now also triggers the FR-001 `ownerReferences` write            |
| `Terminating` (Product)   | deletion marker + foreground-deletion finalizer   | system deletion flow (new, FR-004/FR-011) | `True` while the product is marked as being deleted and its live-variant count has not yet reached zero at removal time |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of product deletions (via git push or the GraphQL mutation) attempted against a product with at least one live variant are rejected, with zero instances of such a product's record being removed.
- **SC-002**: 100% of product deletions attempted against a variant-free product proceed successfully.
- **SC-003**: 100% of eligible product deletions pass through a visibly distinguishable in-progress (`Terminating`) state before the record is removed, with zero instances of a product record disappearing without first being observable in that state.
- **SC-004**: 100% of product deletion requests against a product already marked as being deleted are treated as redundant, with zero instances of a second, independently-tracked deletion attempt being created.
- **SC-005**: Zero instances, across all deletion outcomes, of a `ProductVariant` being left referencing a product name that no longer resolves to any existing record.
- **SC-006**: 100% of resolved `spec.productRef` relationships have a corresponding `metadata.ownerReferences` entry with `blockOwnerDeletion: true`, and the deletion-blocking check (FR-002) is answerable via a single indexed `ownerReferences` lookup rather than a full scan of `ProductVariant` records for a name match.
- **SC-007**: 100% of `ProductVariant` creation attempts against a `Terminating` `Product` are admitted (not rejected for that reason alone), and 100% of them correctly withhold that product's final removal for as long as they exist.

## Assumptions

- **Pure-block relationship, no decouple side**: Unlike spec 052's `CategoryTaxonomy`, which split dependents into a blocking type (children) and a decoupling type (assigned products), `ProductVariant → Product` has only the blocking type. This is a direct consequence of `spec.productRef` being required (ADR-0005) with no safe "unset" state, unlike `spec.categoryRef` on `Product`.
- **Synchronous `ownerReferences` write, matching existing `ProductResolved` resolution**: Because no controller resolves `ProductVariant.spec.productRef` asynchronously today (resolution happens entirely inside git-push admission), this spec's `ownerReferences` write happens at the same synchronous point, not via a new asynchronous path.
- **New minimal `product` reconciler package required**: `gitstore-controller-manager/internal/` has no `product` or `productvariant` package today. This spec introduces a new, minimal `internal/product` package — mirroring `internal/namespace`'s precedent — scoped only to the drain/re-check/finalizer-removal sequence (FR-007, FR-011), not a general-purpose Product reconciler (`categoryRef` resolution, media resolution, etc. remain out of this spec's scope, whether or not they are later migrated to this same package by a future spec).
- **New `deleteProduct` GraphQL mutation, not a bug fix**: No `createProduct`, `updateProduct`, or `deleteProduct` mutation exists in the GraphQL schema today. This spec adds only the minimal `deleteProduct` mutation (and its input/payload types) needed to satisfy FR-003; `createProduct`/`updateProduct` remain git-push-only and out of scope.
- **New variant creation against a `Terminating` product is intentionally allowed**: This is a deliberate departure from spec 052's precedent (which rejects new dependents against a `Terminating` parent/namespace), driven directly by GH#377's own race-safety acceptance criterion. See Clarifications for the full reasoning.
- **`ConditionTerminating` is reused, not redefined**: The condition-type constant already exists in `gitstore-api/internal/catalog` (used by spec 052 for `CategoryTaxonomy`) and is reused as-is for `Product`; this spec does not introduce a new condition-type vocabulary.
- **Per-resource finalizer constant, not a shared one**: Following spec 046's precedent (`datastore.NamespaceForegroundDeletionFinalizer`, `namespace.ForegroundDeletionFinalizer`), this spec introduces Product-specific equivalents (e.g. `datastore.ProductForegroundDeletionFinalizer`, `product.ForegroundDeletionFinalizer`) rather than a shared cross-resource constant.
- **Scope boundary with spec 052 and ADR-0005's own deletion semantics**: This spec does not revisit `CategoryTaxonomy`'s deletion semantics (spec 052's territory) or `ProductVariant`'s own deletion lifecycle beyond the `ownerReferences` entry it writes and implicitly removes when the variant itself is deleted (ADR-0005, unchanged).
