# Research: Controller-Manager Service-Account Authentication (Phase 1)

**Scope note**: `docs/implementation/021-controller_service_account_auth.md` is itself the product of a 102-agent deep-research workflow (20 sources, 21 verified claims) plus direct source inspection, already covering the options comparison (§5), Kubernetes-model analysis (§4), and credential-contract design (§9) this spec needs. This file does **not** re-derive any of that. It records only (a) what was newly verified against the current codebase while writing this spec, (b) drift found versus doc 021's citations, and (c) the scope/phasing decisions this spec's own Spec-Kit formalization required that doc 021 left open.

## 1. Doc 021's design is adopted verbatim — no re-litigation

**Decision**: Option B (§5) — extend GitStore's pluggable AuthN architecture with a GitStore-issued service-account identity plane (`serviceaccount-jwt` + `serviceaccount-assertion`) — is this spec's chosen architecture, exactly as doc 021 §17 concludes. Kubernetes-issued tokens (Option A), an external OAuth2/OIDC AS (Option C), SPIFFE/SPIRE (Option D), mTLS (Option E), and the status quo (Option F) remain rejected for the reasons doc 021 §5's comparison table already gives.

**Rationale**: Doc 021 is already a thorough, source-verified design document with "Status: Proposed" and explicit direction from the task that commissioned this spec to treat it as authoritative background, not re-derive its research. Re-running that comparison would duplicate work with no new information.

## 3. Three `graphqlclient.Client` construction call sites, not one

**Finding**: `registerNamespace`, `registerCategoryTaxonomy`, and `registerProductWatch` in `gitstore-controller-manager/cmd/controller/main.go` each independently call `graphqlclient.New(cfg.Controller.ApiURI, cfg.Controller.ApiToken)`, constructing three separate `*graphqlclient.Client` values that happen to share the same static token today.

**Decision**: When User Story 4 replaces `Client.token string` with `Client.credentials CredentialSource`, `main.go` MUST be refactored to construct exactly **one** `CredentialSource` (and, ideally, one shared `*graphqlclient.Client`, or at minimum one shared `CredentialSource` passed to three `graphqlclient.New`-equivalent constructions) at the top of `main()`, then pass it into all three `registerX` functions — not one independently-renewing `ServiceAccountSource` per call site.

**Rationale**: A `ServiceAccountSource` performs a real network exchange (sign assertion → `issueServiceAccountToken`) on every renewal. Three independent instances would triple the exchange rate for no benefit, would each maintain their own cached-token/renewal-goroutine state (memory and goroutine overhead, plus three independent renewal-jitter schedules that could each fail independently and confusingly), and would make the health-readiness signal (FR-016) ambiguous — "the controller is not ready" would need to mean "none of three independent sources have a token" rather than one clear signal. A single shared `CredentialSource`, injected into all three registration call sites, is both cheaper and gives one unambiguous readiness signal.

**Alternatives considered**: Leave three independent `ServiceAccountSource` instances (simplest diff, mirrors today's three independent `New()` calls exactly). Rejected for the reasons above — it is not simpler in any way that matters once a `CredentialSource` performs real, rate-limited work instead of returning an immutable string.

## 4. Spec 060 does not create a hard technical dependency — the coupling is architectural

**Finding**: Traced end-to-end: `Makefile`'s `bootstrap-token` target issues a `curl`+`jq`-based `login` GraphQL mutation call with no reference to any AuthN provider package; `gitstore-api/cmd/gitctl/main.go` has exactly one subcommand (`hash-password`) and no `staticadmin` import; `gitstore-controller-manager/internal/graphqlclient/client.go` treats its token as an opaque string with no provider-awareness at all. None of these three surfaces would fail to compile or fail at runtime if `static-admin` were deleted and `static-users` (spec 060) took its place — an operator could mint a `static-users` token via `bootstrap-token` and paste it into `GITSTORE_CONTROLLER__API_TOKEN` exactly as before.

**Decision**: Do not claim a hard, code-level blocking dependency between spec 060 and this spec. Instead, state the actual coupling precisely (spec.md's dedicated "Relationship to Specs 059, 060, and Doc 021" section): the reason this spec should land before or alongside spec 060 is that 060's removal of `static-admin` leaves `static-users` (a human-identity, HTTP-Basic-Auth-shaped provider) as the *only* remaining locally-available credential-minting path — which is architecturally wrong for a non-human controller process, and is exactly the anti-pattern doc 021 exists to eliminate. Landing this spec first avoids a real, if temporary, regression: an operator following spec 060's own migration guidance with no service-account alternative available would have to create a fake "human" `users.yaml` entry for `gitstore-controller-manager`.

**Rationale for stating it this way rather than as a hard blocker**: Overstating the dependency (claiming a compile break that does not exist) would be inaccurate and would misrepresent spec 060's own scope (which explicitly states it makes no `gitstore-controller-manager` change). Understating it (claiming no relationship at all) would ignore the real, documented anti-pattern doc 021 was commissioned to close and the urgency framing this spec was explicitly asked to carry. The precise, verified framing serves both a future reader auditing this spec's claims and the immediate goal of sequencing this spec appropriately relative to spec 060's PR #405.

**Alternatives considered**: Asserting a hard blocking dependency without verifying it first. Rejected — this spec's own instructions explicitly required checking doc 021's citations against the current codebase rather than transcribing them, and the same standard applies to the urgency framing itself, not only to line-number citations.

## 5. Phase sequencing: doc 021 §14 vs. this spec's user-story priorities

**Finding**: Doc 021 §14's Phase table orders work as: 1 (persistent identity + providers + issuance + CRUD), 2 (`gitctl` enrollment), 3 (controller-side `CredentialSource`/renewal), 4 (WebSocket `InitFunc`), 5 (default-chain flip + `policy.yaml` shipped default), 6 (future, optional, in-cluster). Doc 021 §11 gives a slightly different phase breakdown, and doc 021 itself flags its own §14 as "likely authoritative" since it appears later in the document — this spec follows that self-correction and treats §14 as authoritative, per the task's own instruction to reconcile the two in favor of §14 if they differ.

**Decision**: This spec's User Story priorities reorder doc 021 §14's Phases 2 and 3 by actual urgency to the stated goal (unblocking spec 060): Phase 1 → User Stories 1–3 (P1, sufficient on its own to unblock spec 060 via a manually-minted token, per Decision 4 above); Phase 3 (controller-side renewal) → User Story 4 (P2); Phase 2 (`gitctl` enrollment) → User Story 5 (P2); Phase 4 (WebSocket) → User Story 6 (P3, since today's read path is ungated regardless — see Decision 6). Phase 5 (flipping the *default* chain, shipping a default `policy.yaml` role) is deferred to this spec's own `tasks.md` final phase and explicitly excluded from this spec's Success Criteria, matching how spec 060 independently owns the analogous default-chain decision for human providers. Phase 6 (in-cluster K8s-issued tokens) remains out of scope, exactly as doc 021 itself scopes it.

**Rationale**: The task's own scoping instruction was explicit — "Phases 2-6 ... can be later phases of THIS spec's own tasks.md ... use your judgment on how to phase tasks.md." Ordering User Story 4 (renewal) ahead of User Story 5 (enrollment tooling) rather than doc 021's own 2-then-3 ordering reflects that automatic renewal closes a bigger operational gap (manual token refresh every ~8 minutes is far more painful than manually running a few enrollment mutation calls once per deployment) — though the two are independent and could be built in either order without blocking each other, which is why both are P2 rather than one being P1 and the other P3.

## 6. Why WebSocket `InitFunc` (US6) is P3, not P1, despite being a real, traced gap

**Finding**: Doc 021 §10a already establishes that GitStore's GraphQL read path (queries and subscriptions) is not gated by any `rbac-local` action check today — only specific mutations (`updateCategoryStatus`, `updateResourceStatus`, and the field-level checks `GraphQLFieldAuthorizer` implements) are enforced. This means an unauthenticated or wrongly-authenticated `connection_init` payload today does not grant access to anything a correctly-configured `rbac-local` policy would otherwise deny, because there is no read-path enforcement to bypass yet.

**Decision**: Confirmed unchanged from doc 021. This spec still implements the `InitFunc`/live-connection-registry work (User Story 6) because it is a correctness property this identity plane should have from the start (a service account's WebSocket connection should not outlive its token or its account's disablement, once a real credential lifecycle exists via User Story 4) — but it is explicitly P3, not P1, precisely because it is closing a proactive gap, not an active one, and doc 021's own Phase ordering (Phase 4, after Phase 3's renewal work) already reflects this.

## 7. `ServiceAccount` persistence template: `File` (spec 051), not a new pattern

**Finding**: `gitstore-api/internal/datastore/entities.go`'s `File` struct and its `Datastore` interface methods (`CreateFile`/`GetFile`/`GetFileByName`/`ListFiles`/`UpdateFile(ctx, f, expectedResourceVersion)`/`DeleteFile`/`DeleteFileWithResourceVersion`/`UpdateFileStatus`) are implemented once in `gitstore-api/internal/datastore/memdb/backend.go` (not a separate per-entity memdb file) and once in `gitstore-api/internal/datastore/scylla/file.go`, with its own numbered migration `gitstore-api/internal/datastore/scylla/migrations/004_file_resource.cql`.

**Decision**: `ServiceAccount` follows this exact template: a new struct in `entities.go`, new interface methods on `Datastore`, an implementation added to the existing `memdb/backend.go` (not a new file, matching `File`'s precedent), a new `scylla/serviceaccount.go`, and a new `scylla/migrations/007_service_account.cql`. This template extends to the **schema itself**, not just the file layout: `004_file_resource.cql`'s canonical envelope column names and types (`creation_timestamp`/`update_timestamp`/`deletion_timestamp`, `creation_actor`/`update_actor`, `generation bigint`, `resource_version text`, `uid uuid`), its query-first `_by_namespace`/`_by_name`/`_by_uid` table triple, and its `gocql.UUID`-in-row / `string`-in-entity boundary conversion. `002_secondary_indexes.cql` records that the alpha baseline intentionally ships **zero** secondary indexes, and spec 048 removed the ones Repository had; ServiceAccount adds none. See data-model.md for the resulting CQL.

**Rationale**: Doc 021 §8c already mandates that the ServiceAccount record be datastore-backed in both memdb and Scylla from the first implementation phase; `File` (spec 051, the most recently shipped new persisted entity) is the closest, most current precedent for exactly this shape of work, and reusing it avoids inventing a fourth persistence pattern alongside `File`'s, `Repository`'s (spec 045/058), and `Namespace`'s (spec 046).
