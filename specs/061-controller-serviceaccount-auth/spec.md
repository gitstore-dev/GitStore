# Feature Specification: Controller-Manager Service-Account Authentication (Phase 1)

**Feature Branch**: `061-controller-serviceaccount-auth`

**Created**: 2026-08-29
**Status**: Draft
**Input**: User description: "Formalize `docs/implementation/021-controller_service_account_auth.md` (Status: Proposed, no code changes made) as a Spec Kit feature spec, scoped urgently to unblock spec 060 (`specs/060-local-multiuser-authn/`, open draft PR #405). Spec 060 removes the `static-admin` AuthN provider entirely and replaces it with `static-users`, a local multi-user human-identity provider. `gitstore-controller-manager`'s only way to obtain a working credential today is a `static-admin`-issued bearer JWT (`Roles: ['admin']`) manually minted and pasted into `GITSTORE_CONTROLLER__API_TOKEN`. Doc 021 already decided (§5, §17) to extend GitStore's pluggable AuthN architecture with a GitStore-issued service-account identity plane — a `serviceaccount-jwt` AuthN provider plus a `serviceaccount-assertion` proof-of-possession issuance provider, modeled on Kubernetes ServiceAccount/TokenRequest properties without requiring Kubernetes. This spec formalizes doc 021's already-designed interfaces (§8), claim contracts (§9), and phased rollout (§14) into Spec Kit format, scoped so its own User Story 1/P1 is exactly 'the controller-manager can obtain and use a working credential without `static-admin` (or, after spec 060, `static-users`) existing' — the minimum needed to keep spec 060 from forcing the controller-manager to either keep a deleted provider alive or be re-plumbed through a human multi-user credential mechanism it structurally does not belong in."

## Relationship to Specs 059, 060, Doc 021, and ADR 0009 *(mandatory context — read before Requirements)*

### Derivation from ADR 0009 (credential and secret material boundary)

This spec **derives from** [ADR 0009: Credential and Secret Material Boundary](../../docs/ADRs/0009-credential-secret-boundary.md), which was written specifically to prevent this spec from shipping a second, parallel credentialing system alongside [ADR 0001](../../docs/ADRs/0001-secretref-reference-contract.md)'s `SecretRef`.

The two concerns are genuinely distinct layers and neither subsumes the other — ADR 0001 answers *"where is the secret material this **resource** needs?"* (data plane, authored in Git, resolved on a resource's behalf), while this spec answers *"how does this **process** prove who it is?"* (control plane, deployment-configured, acting as itself). `CredentialSource` is therefore not a duplicate of `SecretRef`.

The overlap ADR 0009 closes is narrower and concrete: **both ultimately need secret bytes loaded into a process.** This spec's earlier draft read its `ServiceAccount` private key from a bespoke `GITSTORE_CONTROLLER__SERVICEACCOUNT__PRIVATE_KEY_FILE` filesystem path — provider topology hard-coded into deployment configuration, with no resolver indirection and no shared error taxonomy, which is exactly the coupling ADR 0001 exists to prevent for manifests. Per ADR 0009:

- The signing key is now located by an ADR 0001 `SecretRef` and obtained through a **bootstrap-tier** `SecretResolver` (FR-015a). The `type: file` bootstrap provider is the supported local-development and Docker-Compose replacement for the removed path variable.
- The **bootstrap tier** exists because a process's identity key is the credential it needs *in order to* reach the network — resolving it through a provider that itself requires a GitStore-issued credential is circular. Bootstrap-tier resolvers therefore must not make any network call that depends on a GitStore credential (ambient platform credentials such as IRSA/workload identity remain permitted), and must never be used to satisfy a resource-authored `SecretRef` (FR-015b).
- `ServiceAccount` **public** keys are not secret material and correctly remain in the datastore, outside this boundary entirely — ADR 0009 §5 states this explicitly so the distinction is not re-litigated during implementation.
- ADR 0009 also specifies `CredentialsRef`, which ADR 0001 named but left undefined; this spec does not itself author any `CredentialsRef`, but the specification closes the ambiguity that allowed this spec's drift in the first place.

**Prerequisite this creates**: a minimal file-based bootstrap `SecretResolver` must exist before this spec's User Story 4 (controller-side credential acquisition) can land. This is a small addition to this spec's critical path, recorded as a negative consequence in ADR 0009 and reflected in `tasks.md`.

### Relationship to specs 059 and 060

GitStore's AuthN architecture (`docs/implementation/020-pluggable_auth_architecture.md`) now has three distinct, non-overlapping principal types, each solving a different identity problem:

| Spec | Principal type | Availability | Problem solved |
|---|---|---|---|
| **059** (`059-optional-oidc-provider`) | Human, via an external/bring-your-own OIDC IdP | Optional (operator supplies `issuer_url`, or deploys the optional reference Hydra+Kratos stack this spec adds) | Standards-compliant SSO for organizations that already have, or want, a real IdP. |
| **060** (`060-local-multiuser-authn`) | Human, local | Always available (mandatory core, no external dependency) | More than one named local human account, replacing `static-admin`'s single hardcoded credential; "admin" becomes purely an `rbac-local` role, not a code concept. |
| **061 (this spec)** | Non-human (controller-manager, and future controllers) | Always available (mandatory core, no external dependency) | A self-renewing, least-privilege, audience-bound credential for a machine caller — never indistinguishable from a human in the audit trail, never an `admin`-role token pasted into an env var. |

None of these three specs modifies another's provider code. They compose in the same `auth.authn.chain` (e.g. `["static-users","serviceaccount-assertion","serviceaccount-jwt","oidc-jwt","anonymous"]`) because `ChainedAuthN` already dispatches by `OutcomeChallenge`/"not my token, try next" (`020-pluggable_auth_architecture.md` §Decision 2; re-confirmed unchanged in `gitstore-api/internal/auth/registry.go`).

**Ordering relationship with spec 060 (verified against the current codebase, not assumed):**

- Spec 060's `plan.md` states plainly it makes **no** `gitstore-controller-manager` change; it is scoped entirely to `gitstore-api`. Mechanically, `gitstore-controller-manager/internal/graphqlclient.Client` (`Client.token string`, set once in `New(baseURL, token string)`, confirmed at `gitstore-controller-manager/internal/graphqlclient/client.go`) and the `Makefile`'s `bootstrap-token` target (confirmed: it calls the generic GraphQL `login` mutation over HTTP/`curl`+`jq`, with **no Go-level import of `staticadmin`, `gitctl`, or any provider package**) are both provider-agnostic — they work with a bearer token minted by *any* currently-active local credential provider, not specifically `static-admin`. There is therefore **no compile-time or hard runtime break** if spec 060 merges before this spec: an operator could still run `make bootstrap-token` against a `static-users` identity and paste the resulting token into `GITSTORE_CONTROLLER__API_TOKEN`, exactly as they do today with `static-admin`.
- The real coupling this spec closes is **architectural, not mechanical**: without this spec, the *only* available way to mint a controller credential after spec 060 ships would be creating a `static-users` entry — i.e., a `{username, bcrypt password_hash}` row in `users.yaml`, HTTP-Basic-Auth-shaped, meant for a *named human operator* — for a non-human controller process. That is precisely the anti-pattern doc 021 was commissioned to eliminate (doc 021 §3, Required Property #1: "a controller must never be indistinguishable from a human admin in the audit trail"), and it would have to be introduced by spec 060's own migration and then torn out again once this spec lands — churn this spec avoids by landing first, or in the same release window.
- `docs/implementation/021-controller_service_account_auth.md` §2 explicitly cites `specs/040-controller-watch-status-api/research.md:45-50`'s decision — *"The controller-manager authenticates as an ordinary bearer-JWT principal (issued via the existing `staticadmin.IssueSession`/`gitctl` tooling)..."* — as the interim status quo this spec supersedes. That citation is a documented **design decision**, not a Go import; `gitctl` (`gitstore-api/cmd/gitctl/main.go`) has exactly one subcommand today (`hash-password`) and contains no reference to `staticadmin` at all. Doc 021's own header line already states it "supersedes spec 040 research.md's ... interim decision" — this spec is where that supersession is formally implemented.
- **Conclusion**: this spec SHOULD land before or in the same release window as spec 060, not because 060 breaks the controller-manager, but because 060 is the trigger that makes the controller-manager's status quo (a manually-copied, `admin`-role bearer token) visibly indefensible — its only remaining "local, always-available" minting path would otherwise become a human-identity provider never designed to represent a machine. Landing this spec first (or alongside) means spec 060's own migration documentation can point operators who ask "how do I authenticate `gitstore-controller-manager` now?" at `serviceaccount-jwt`, not at creating a fake human user.
- This spec does **not** block spec 060 from merging on its own technical merits — 060 is independently correct and independently testable per its own spec. The two specs' `role_bindings`/`policy.yaml` surfaces are additive to each other (spec 060 adds human `role_bindings` entries such as `alice: [admin]`; this spec adds machine `role_bindings` entries such as `serviceaccount:controllers:gitstore-controller-manager: [gitstore-controller-manager]`), and neither spec's tests depend on the other's provider existing.

**Scope boundary vs. doc 021's own phases**: this spec's Priority 1 user stories are scoped to exactly doc 021 §14 Phase 1 (persistent ServiceAccount datastore model; `serviceaccount-assertion`/`serviceaccount-jwt` providers, opt-in via explicit chain config; assertion-gated `issueServiceAccountToken`; administrative ServiceAccount/key lifecycle mutations) — this is the minimum that lets an operator mint a legitimate, non-human, least-privilege credential without `static-admin` or `static-users` existing, using nothing beyond `gitstore-api` itself (a token minted this way can be pasted into `GITSTORE_CONTROLLER__API_TOKEN` exactly like today's static-admin token, with zero `gitstore-controller-manager` code change, because `graphqlclient.Client` already treats its token as an opaque bearer string). Doc 021 §14 Phases 2–6 (control-manager-side automatic renewal, `gitctl` enrollment tooling, WebSocket `InitFunc`/live-connection revocation, default-chain flip) are included as this spec's own P2/P3 user stories and later `tasks.md` phases, not deferred to a separate spec, because they share every datastore/provider/contract surface this spec's P1 work introduces and splitting them would only fragment one coherent identity-plane rollout.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - An operator can mint a working, non-human controller credential without `static-admin` or `static-users` existing (Priority: P1)

Today, the only way to give `gitstore-controller-manager` a working credential is for an administrator to hold a `static-admin`-issued (`Roles: ["admin"]`) bearer token and paste it into `GITSTORE_CONTROLLER__API_TOKEN`. Once spec 060 removes `static-admin`, that path is gone; the only remaining option would be minting a human-shaped `static-users` credential for a non-human process. An operator instead needs a way to register a durable, namespaced, non-human identity (a `ServiceAccount`) with `gitstore-api`, and to exchange proof of possession of that identity's private key for a short-lived access token — entirely independent of whatever human-facing AuthN provider(s) are or are not chained in.

**Why this priority**: This is the specific requirement that unblocks spec 060 (see "Relationship to Specs 059, 060, and Doc 021" above) and the foundational capability every other user story in this spec depends on. Without it, nothing else in this spec has an identity to operate against.

**Independent Test**: Can be fully tested by registering a `ServiceAccount` and one public key through the administrative mutations (User Story 2), signing a client assertion with the matching private key entirely outside `gitstore-controller-manager` (e.g., with a small test harness or `openssl`), calling `issueServiceAccountToken`, receiving a short-lived access token, and successfully issuing an authenticated GraphQL query with that token — all without any `static-admin` or `static-users` identity existing anywhere in the deployment.

**Acceptance Scenarios**:

1. **Given** a registered, enabled `ServiceAccount` with one enrolled public key, **When** a caller signs a client assertion with the matching private key and submits `issueServiceAccountToken`, **Then** the request succeeds and returns a short-lived access token and its expiry.
2. **Given** the same `ServiceAccount`, **When** a caller submits `issueServiceAccountToken` with an assertion signed by a private key that does not correspond to any of the account's enrolled public keys, **Then** the request is denied and no token is issued.
3. **Given** a validly issued access token, **When** it is presented as `Authorization: Bearer <token>` on a GraphQL HTTP query or mutation, **Then** `serviceaccount-jwt` authenticates it and the request proceeds as that `ServiceAccount`'s principal — with no `static-admin` or `static-users` provider chained in at all.
4. **Given** an access token whose `exp` has passed, **When** it is presented on any GraphQL request, **Then** authentication fails and the caller must exchange a fresh assertion to continue.
5. **Given** a bearer token issued by a different, unrelated provider (or no token at all), **When** it reaches `serviceaccount-jwt`, **Then** the provider returns "not my token" (`OutcomeChallenge`) rather than denying outright, preserving existing chain fallthrough semantics.
6. **Given** `serviceaccount-assertion`/`serviceaccount-jwt` are absent from `auth.authn.chain` (the unchanged default), **When** the server starts, **Then** it starts exactly as it does today — both providers are strictly opt-in and introduce no behavior change for a deployment that does not list them.

### User Story 2 - An administrator can create, enroll keys for, rotate keys for, and delete ServiceAccounts (Priority: P1)

User Story 1 is unusable without a way to first create the `ServiceAccount` identity and register its public key. An administrator (an already-authenticated, already-authorized principal — human or, recursively, another sufficiently-privileged service account) needs mutations to create a `ServiceAccount`, enroll or rotate its public keys (supporting an overlap window so old and new keys both verify during rotation), and delete or disable it — with deletion/disable taking effect immediately for future authentication and issuance attempts.

**Why this priority**: Equal in importance to User Story 1 — an identity plane with no lifecycle management is not administrable, and doc 021 treats CRUD and issuance as one inseparable Phase 1 deliverable.

**Independent Test**: Can be fully tested by calling `createServiceAccount` with an initial public key, confirming `issueServiceAccountToken` then succeeds for that key; calling `rotateServiceAccountKey` to add a second key and remove the first, confirming the first key's assertions are rejected and the second's succeed; then calling `deleteServiceAccount` and confirming both keys are rejected afterward.

**Acceptance Scenarios**:

1. **Given** an authenticated principal authorized for ServiceAccount administration, **When** `createServiceAccount` is called with a namespace, name, and one or more public keys, **Then** a new `ServiceAccount` record is persisted with a UID, `disabled=false`, and the submitted keys, and the response returns that UID.
2. **Given** an existing `ServiceAccount`, **When** `createServiceAccount` is called again for the same namespace/name, **Then** the request is rejected — namespace/name pairs are unique.
3. **Given** an existing `ServiceAccount` with key `kid=A`, **When** `rotateServiceAccountKey` adds `kid=B` without removing `kid=A`, **Then** assertions signed by either key are accepted (overlap window) until `kid=A` is explicitly removed in a later call.
4. **Given** the same account after `kid=A` is removed via `rotateServiceAccountKey`, **When** an assertion signed with the now-removed `kid=A` is submitted, **Then** issuance is denied.
5. **Given** an existing `ServiceAccount`, **When** `deleteServiceAccount` is called, **Then** subsequent assertion exchanges and any already-issued access tokens for that account's subject are rejected by their respective providers.
6. **Given** a principal that is not authorized for ServiceAccount administration, **When** any of `createServiceAccount`/`rotateServiceAccountKey`/`deleteServiceAccount` is called, **Then** the request is denied and no ServiceAccount state changes.
7. **Given** a `ServiceAccount` is deleted and, hypothetically, a new one is later created with the same namespace/name, **When** a token issued against the old UID (if somehow still unexpired) is presented, **Then** it is rejected on UID mismatch against the new record — a deleted-and-recreated identity is never confused with its predecessor.

### User Story 3 - A controller's token carries least privilege, never `admin`, and is scoped by the same `rbac-local` mechanism as any other subject (Priority: P1)

An operator wants the `gitstore-controller-manager` to receive exactly the actions its reconcilers need and nothing more — never a blanket `admin` role. Role assignment must flow through `rbac-local`'s existing `role_bindings` map, keyed on the service account's stable subject string, with zero `rbac-local` source changes, exactly mirroring how spec 060 makes `role_bindings` load-bearing for human identities.

**Scope note (added 2026-08-30, on rebase onto spec 047 / PR #370)**: `gitstore-controller-manager` does not run only the CategoryTaxonomy reconciler. `cmd/controller/main.go` registers **three** workloads — `registerNamespace`, `registerCategoryTaxonomy`, and `registerProductWatch` — and User Story 4 deliberately consolidates them onto **one shared `CredentialSource`**, hence **one service account**. That account's role is therefore the *union* of all three workloads' required actions, not just CategoryTaxonomy's:

| Workload | GraphQL operation | Required action |
|---|---|---|
| `registerCategoryTaxonomy` | `updateCategoryStatus` | `category.status.write` |
| `registerCategoryTaxonomy` | category delete finalization | `category.delete` |
| `registerNamespace` | `createRepository` (system-repo provisioning) | `repository.create.any` — see below |
| `registerNamespace` | `completeNamespaceDeletion` | `namespace.status.write` |
| `registerNamespace` / `registerProductWatch` | list/watch queries | reserved `category.list`/`category.watch`/`product.list`/`product.read.unpublished` |

**`repository.create.any` is unavoidable, and is this spec's sharpest least-privilege tension.** `Resolver.authorizeRepositoryTenant` (`gitstore-api/internal/graph/resolver/repository_authorization.go`) derives the action's `.own`/`.any` suffix by comparing `namespace.CreationActor` against `principal.Subject`, falling back to `.any` whenever they differ. A controller's subject (`serviceaccount:controllers:<name>`) can never equal a human-created namespace's `CreationActor` (e.g. `alice`), so **every** system-repository provisioning call by the controller resolves to `repository.create.any` — normally an admin-tier action. Spec 047 makes this load-bearing rather than theoretical, since system-repository provisioning is now on the enforced namespace-admission path. This spec MUST grant `repository.create.any` and MUST document why, rather than claiming a tighter grant it cannot actually achieve; narrowing it (e.g. a resource-context predicate restricting the grant to the reserved system-repository name, or an explicit machine-actor scope rule) requires an `rbac-local` policy-semantics change that FR-021 forbids here and is recorded as a follow-on concern.

**Independently confirmed by the shipped dev policy (#410).** `config/policy.yaml`, committed by #410 and mounted into `api`, already defines a `controller` role granting `*.status.write`, `category.status.write`, and `namespace.status.write` — and **no** `repository.create.any`. That role is therefore already insufficient for the namespace reconciler's system-repository provisioning path, and its binding is keyed on the bare subject `controller` rather than a service-account subject. This spec MUST update `config/policy.yaml`'s `controller` role to the union role above and re-key its binding to `serviceaccount:controllers:gitstore-controller-manager`.

**Why this priority**: Equal in importance to User Stories 1–2 — an identity plane that still hands out `admin`-equivalent tokens has not actually fixed the problem this spec exists to fix; least privilege is the whole point, not an enhancement layered on afterward.

**Independent Test**: Can be fully tested by binding `serviceaccount:controllers:gitstore-controller-manager` to a role granting only the actions in the table above in `policy.yaml`, authenticating as that service account, and confirming it can perform `category.status.write` and `repository.create.any` but is denied actions outside the table (e.g., `namespace.delete.any`, `repository.delete.any`) — using the same unmodified `rbac-local` provider spec 060 already re-confirms needs no code change.

**Acceptance Scenarios**:

1. **Given** `role_bindings` mapping the controller's subject to a role permitting only the actions in the table above, **When** that service account authenticates and calls `updateCategoryStatus`, **Then** the action is allowed.
2. **Given** the same binding, **When** that service account attempts an action outside its role's `allow` list (e.g., `namespace.delete.any`), **Then** the action is denied.
3. **Given** any `serviceaccount-jwt`-authenticated principal, **When** its `Roles` field is inspected, **Then** it is always empty — exactly mirroring spec 060's `static-users` design decision that role information exists only inside `rbac-local`'s authorization decision, never on the principal itself (doc 021 §9a's explicit "roles are NOT embedded in the token" design decision).
4. **Given** a `ServiceAccount` with no `role_bindings` entry at all, **When** it authenticates and attempts any action under `rbac-local` with `default_deny` true (the default), **Then** every action is denied — there is no other path by which a service account could be granted a role.
5. **Given** the controller's service account bound to the role above, **When** `registerNamespace`'s reconciler provisions a system repository into a namespace whose `CreationActor` is a human user, **Then** `authorizeRepositoryTenant` resolves the action to `repository.create.any` and the call is allowed — verifying that the role grants the action the code actually requests, not the `.own` variant it does not.
6. **Given** the same binding, **When** the namespace reconciler calls `completeNamespaceDeletion`, **Then** `namespace.status.write` is allowed, and **When** it attempts `deleteNamespace` itself, **Then** the action is denied — the controller finalizes deletions it did not authorize.

### User Story 4 - The controller-manager acquires and renews its own credential automatically, including after extended downtime (Priority: P2)

Once User Stories 1–3 exist, an operator can already run the controller by manually minting a token and pasting it into `GITSTORE_CONTROLLER__API_TOKEN` — functionally unblocking spec 060, but with the same manual-renewal burden `static-admin` tokens always had (worse, since access tokens here are deliberately short-lived, 10 minutes by default). The controller-manager itself should sign its own assertions from a locally-held private key, exchange them for access tokens, cache and proactively renew them before expiry, and recover automatically after downtime longer than one token's lifetime — with no administrator step at startup or restart.

**Why this priority**: Lower urgency than User Stories 1–3 because the manual-token path already satisfies the literal "unblock spec 060" requirement; this story is what makes the credential production-usable rather than merely possible.

**Independent Test**: Can be fully tested by starting `gitstore-controller-manager` with an enrolled private key and `ServiceAccount` identity (no `GITSTORE_CONTROLLER__API_TOKEN` set), confirming it becomes ready without any administrator action, then stopping it past its access token's expiry and confirming it becomes ready again on restart without any token having been manually refreshed.

**Acceptance Scenarios**:

1. **Given** a controller-manager configured with a `ServiceAccount` identity, key ID, and private-key file (no static token), **When** it starts, **Then** it signs a client assertion, exchanges it for an access token, and begins normal operation without administrator involvement.
2. **Given** a running controller-manager, **When** its cached access token approaches expiry, **Then** it proactively exchanges a fresh assertion before the old token expires, with no interruption to in-flight GraphQL calls.
3. **Given** a controller-manager that has been stopped for longer than its access token's lifetime, **When** it is restarted, **Then** it obtains a new access token directly from its enrolled private key, with no dependence on the previous (now-expired) token.
4. **Given** `GITSTORE_CONTROLLER__API_TOKEN` is set and no `ServiceAccount` signer is configured, **When** the controller-manager starts, **Then** it uses the static token exactly as it does today — this is an explicit, documented, deprecated dev/CI compatibility path (see "Migration for `GITSTORE_CONTROLLER__API_TOKEN`" below), not removed by this spec.
5. **Given** the token-issuance endpoint is unreachable at startup, **When** the controller-manager retries, **Then** it applies jittered backoff rather than a tight retry loop, and its readiness endpoint reports not-ready until a token is obtained.

### User Story 5 - Enrolling a controller identity is a scriptable, idempotent operation, never a bearer-token copy (Priority: P2)

An operator provisioning a new `gitstore-controller-manager` deployment (native process, Docker Compose, or CI) needs a single, repeatable command that generates or accepts a private key, registers the `ServiceAccount` and its public key with `gitstore-api` using the operator's own already-authenticated administrative session, and never writes a bearer access token to disk.

**Why this priority**: Lower urgency than User Stories 1–4 — hand-rolling the assertion-signing and enrollment mutation calls (e.g., with a small script or `openssl`) is sufficient to validate and even operate this spec's core design, but a dedicated tool is what makes the workflow safe and repeatable for real deployments and CI.

**Independent Test**: Can be fully tested by running the enrollment command twice against the same `ServiceAccount` name with the same key material and confirming the second run is a no-op (idempotent), then confirming the private key file it wrote is never transmitted to `gitstore-api` and no bearer token appears in the command's output or in any file it writes.

**Acceptance Scenarios**:

1. **Given** a fresh deployment with an authenticated administrative session available, **When** the enrollment command is run for a new `ServiceAccount` name, **Then** it creates the `ServiceAccount`, registers its public key, and writes only the private key (with restrictive file permissions) locally — no bearer token is written anywhere.
2. **Given** the same command is run again with unchanged inputs, **When** it detects the `ServiceAccount` and key already exist as specified, **Then** it makes no further changes and exits successfully (idempotent).
3. **Given** the command's output or logs are inspected after a run, **When** searched for a bearer/access token value, **Then** none is found.

### User Story 6 - The controller's WebSocket subscription is bound to its access token's lifetime and revoked promptly (Priority: P3)

The controller-manager's `graphqlclient.Client.Subscribe` sends its bearer token once, in the `connection_init` payload, for the life of the WebSocket connection (`gitstore-controller-manager/internal/graphqlclient/client.go`). `gitstore-api`'s current `transport.Websocket` wiring has no `InitFunc`, so that payload is never authenticated today, for any provider. Once User Story 4 gives the controller-manager a real proactive-renewal credential lifecycle, its WebSocket connection should be authenticated at `connection_init`, bounded by the token's expiry server-side (not merely client-side), and torn down immediately if the underlying `ServiceAccount` is disabled or deleted mid-connection.

**Why this priority**: Lowest urgency in this spec — today's GraphQL read path (subscriptions included) is not gated by any `rbac-local` action check at all (doc 021 §10a; unchanged by this spec), so an unauthenticated `connection_init` is not currently a live authorization bypass. This story closes the gap proactively, ahead of any future read-path enforcement work, rather than in reaction to an active vulnerability.

**Independent Test**: Can be fully tested by opening a subscription with a valid service-account access token, confirming it is accepted at `connection_ack`, then disabling the underlying `ServiceAccount` and confirming the open connection is closed immediately without waiting for the token's natural expiry.

**Acceptance Scenarios**:

1. **Given** a `connection_init` payload carrying a valid, unexpired service-account access token, **When** the WebSocket handshake completes, **Then** the connection is accepted and its context is bound to that token's expiry.
2. **Given** a `connection_init` payload carrying an expired, malformed, or absent-credential token, **When** the handshake is attempted, **Then** the connection is rejected before `connection_ack`.
3. **Given** an open, authenticated subscription, **When** its underlying `ServiceAccount` is disabled or deleted, **Then** the connection is closed immediately, without waiting for the access token's natural expiry.
4. **Given** an open, authenticated subscription, **When** its access token's `exp` is reached, **Then** the server-side context deadline closes the connection even if the client sends nothing further — this is the authoritative boundary; client-side proactive reconnect (User Story 4) is a continuity optimization only.

### Edge Cases

- What happens when two `issueServiceAccountToken` requests use the same assertion `jti` (a replay attempt)? (The second exchange is rejected; only the first succeeds. Replay protection is process-local in the single-API-instance profile this spec targets — see Assumptions.)
- What happens when an assertion's `iat`/`nbf` is slightly in the future due to clock drift between the controller-manager host and `gitstore-api`? (Accepted within the configured clock-skew leeway; rejected beyond it.)
- What happens when a client assertion's lifetime exceeds 60 seconds? (Rejected — the assertion contract caps lifetime at 60 seconds regardless of the requested access-token TTL.)
- What happens when a caller requests an access-token TTL longer than `auth.serviceaccount.max_ttl`? (The server clamps the issued token's `exp` to `max_ttl`; it never issues a longer-lived token than configured, regardless of what was requested.)
- What happens when `createServiceAccount` is called with zero public keys? (Rejected — an account with no enrolled key can never successfully exchange an assertion, so this is refused at creation time rather than silently producing an unusable account.)
- What happens to already-open GraphQL HTTP requests in flight when a `ServiceAccount` is disabled mid-request? (The in-flight request completes under the principal state it was authenticated with; only subsequent requests are affected — no mid-request cancellation is introduced by this spec.)
- What happens if `gitstore-controller-manager` is configured with both a `ServiceAccount` signer and a non-empty `GITSTORE_CONTROLLER__API_TOKEN`? (The `ServiceAccount` signer takes precedence — the deprecated static token is a fallback used only when no signer is configured, never a simultaneous alternate credential.)
- What happens when the `gitstore-api` issuer signing key is rotated while a controller holds a not-yet-expired access token signed by the old key? (The old key remains in the trusted verifier set during the configured overlap window, so the existing token continues to validate; only after the overlap window ends and the old key is removed does verification of tokens signed by it stop.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a persistent `ServiceAccount` datastore record (namespace, name, UID, `disabled` state, one or more enrolled public keys with key IDs) that survives `gitstore-api` restart and is implemented against `datastore.Datastore` for both the `go-memdb` development backend and the ScyllaDB production backend, from this spec's first implementation phase.
- **FR-002**: The system MUST provide `createServiceAccount`, `rotateServiceAccountKey`, and `deleteServiceAccount` administrative GraphQL mutations, each authorized so that only a principal already holding sufficient administrative privilege (via the existing `rbac-local`/AuthZ mechanism, not a new hardcoded check) may call them.
- **FR-003**: `createServiceAccount` MUST reject a request for a namespace/name pair that already has a `ServiceAccount` record, and MUST reject a request with zero public keys.
- **FR-004**: `rotateServiceAccountKey` MUST support adding one or more public keys and removing one or more existing key IDs in the same call, and MUST accept assertions signed by any currently-enrolled key — including during a deliberate overlap window where both an old and new key are simultaneously enrolled.
- **FR-005**: `deleteServiceAccount` MUST cause all subsequent assertion-exchange and access-token-authentication attempts for that account's subject to be denied, effective immediately for any request the API processes after the deletion is persisted.
- **FR-006**: The system MUST provide a new `serviceaccount-assertion` AuthN provider that verifies a short-lived (maximum 60 seconds between `iat` and `exp`), signature-checked client assertion against an enrolled `ServiceAccount` public key, and successfully authenticates it only for the single `issueServiceAccountToken` mutation — never for any other GraphQL operation, regardless of the assertion's validity.
- **FR-007**: The system MUST provide a new `serviceaccount-jwt` AuthN provider that verifies API-issued access tokens (`iss`, `aud`, `exp`/`nbf`/`iat` with configured clock-skew leeway, and a private `sa_uid` claim matched against the persistent `ServiceAccount` record) and produces a `Principal` with an empty `Roles` field and `AuthMethod: "serviceaccount-jwt"`.
- **FR-008**: Both new providers MUST return `OutcomeChallenge` (not `OutcomeDeny`) for a bearer token they do not recognize as their own (wrong `iss` or `typ`), preserving `ChainedAuthN`'s existing "try next provider" fallthrough semantics; an invalid-but-recognized token (correct `iss`/`typ` but bad signature, expired, wrong audience, or disabled/deleted account) MUST return `OutcomeDeny`.
- **FR-009**: Both new providers MUST be strictly opt-in via `auth.authn.chain` configuration; a deployment that does not list `serviceaccount-assertion`/`serviceaccount-jwt` in its chain MUST observe zero behavior change from this spec.
- **FR-010**: `issueServiceAccountToken` MUST require the caller to have authenticated through `serviceaccount-assertion` for the exact `ServiceAccount` (matched on subject and UID) the request targets; an access token, a `static-users`/`static-admin` session, or an assertion for a different account MUST NOT authorize issuance.
- **FR-011**: Issued access tokens MUST NOT embed any role or scope claim; authorization for a `serviceaccount-jwt`-authenticated principal MUST be resolved exclusively by the active AuthZ provider (`rbac-local`'s `role_bindings`, keyed on the account's subject string, with zero `rbac-local` source changes) at the time of each request, never by anything carried on the token or the persisted `ServiceAccount` record.
- **FR-012**: Access-token signing MUST use an asymmetric algorithm (Ed25519 preferred, ECDSA P-256 acceptable) exclusively; the `serviceaccount-jwt` issuer/verifier path MUST NOT use a shared-secret (HS256) scheme.
- **FR-013**: The system MUST support signing-key rotation with an explicit overlap window: during rotation, the API MUST continue to accept previously-issued, still-unexpired access tokens signed with the outgoing key until an administrator explicitly ends the overlap window, after which only the new key's signatures verify.
- **FR-014**: `gitstore-controller-manager` MUST continue to accept `GITSTORE_CONTROLLER__API_TOKEN` as a static bearer token exactly as it does today, unmodified in behavior, as an explicit, documented, deprecated dev/CI compatibility path — this spec MUST NOT remove or break that path.
- **FR-015**: `gitstore-controller-manager` MUST support acquiring and proactively renewing its own access token from a locally-configured `ServiceAccount` identity, key ID, and private key, taking precedence over `GITSTORE_CONTROLLER__API_TOKEN` whenever a signer is configured, and MUST recover automatically (no administrator step) after downtime exceeding one access token's lifetime.
- **FR-015a**: The `ServiceAccount` signing private key MUST be located by an ADR 0001 `SecretRef` and obtained through a **bootstrap-tier** `SecretResolver` per [ADR 0009](../../docs/ADRs/0009-credential-secret-boundary.md) §3. No component introduced by this spec may read the private key directly from a configured filesystem path, environment variable, or provider SDK outside a resolver implementation — the previously-drafted `GITSTORE_CONTROLLER__SERVICEACCOUNT__PRIVATE_KEY_FILE` surface is replaced by a `SecretRef` plus a bootstrap provider binding (`file` being the local-development default).
- **FR-015b**: Bootstrap-tier resolution failure MUST be fatal to startup and MUST fail closed using ADR 0001's error classes (`InvalidRef`, `NotFound`, `MissingKey`, `Forbidden`, `ProviderUnavailable`). It MUST NOT fall through to the deprecated `GITSTORE_CONTROLLER__API_TOKEN` path, and MUST NOT be satisfied by a runtime-tier resolver.
- **FR-015c**: No key material introduced by this spec — neither `auth.serviceaccount.signing_key` (the API's access-token signing key) nor the controller's service-account private key — may be placed in a configuration file that is mounted into more than one service. As of #410 (`compose.local.yml`), a single `config/config.toml` is mounted read-only into `git-service`, `api`, **and** `controller-manager` at `/config/gitstore.toml`. Putting the API's signing key in that shared file would let `controller-manager` mint an access token for **any** subject, bypassing the assertion/proof-of-possession flow and every least-privilege guarantee in User Story 3; putting the controller's private key there would let `api` and `git-service` impersonate the controller. Each service's own key material MUST therefore be resolved through a per-service bootstrap `SecretRef` (FR-015a) whose backing source is mounted into that service alone. This applies to the local/dev profile too: the shared-config profile MUST be documented as unable to carry service-account key material, so that no operator generalizes its pattern into production.
- **FR-016**: `gitstore-controller-manager`'s credential-acquisition retry behavior MUST apply jittered backoff on issuance failure and MUST surface "not ready" on its existing health/readiness endpoint until a valid access token is obtained, rather than crash-looping or silently retrying with no observable signal.
- **FR-017**: The system MUST provide (or update) an idempotent enrollment operation that creates/updates a `ServiceAccount` and registers a public key using an already-authenticated administrative session, and MUST NOT write a bearer access token to any file or log as part of that operation.
- **FR-018**: The system MUST add a `transport.Websocket.InitFunc` that authenticates the `connection_init` payload through the same provider chain used for HTTP, rejects anonymous/expired/disabled/deleted/UID-mismatched service accounts before `connection_ack`, and binds the resulting connection's context to a deadline at the authenticated principal's token expiry.
- **FR-019**: The system MUST cancel every live WebSocket connection associated with a `ServiceAccount`'s UID immediately when that account is disabled or deleted, independent of the connection's token expiry.
- **FR-020**: No component introduced by this spec MUST log a raw access token, client assertion, or private key value at any log level.
- **FR-021**: This spec MUST NOT modify `rbac-local`'s `Authorize` decision logic, `policy.yaml`'s schema, or any existing AuthN/AuthZ provider's behavior for principals it does not itself introduce (`static-admin`/`static-users`/`anonymous`/`oidc-jwt`/`allow-all` are unaffected).

### Key Entities

- **`ServiceAccount`**: A persistent, namespaced, non-human identity record (`serviceaccount:<namespace>:<name>` subject, UID, `disabled` state, one or more enrolled public keys with key IDs), the trust anchor for every access token issued for that identity. Datastore-backed (memdb + ScyllaDB), never in-memory-only.
- **Client assertion**: A short-lived (≤60s), signature-proven, single-purpose JWT a caller signs with a `ServiceAccount`'s enrolled private key, presented only to `issueServiceAccountToken`, never usable for any other operation.
- **Access token**: A short-lived (default 10 minutes, capped at a configurable max TTL), asymmetrically-signed JWT `serviceaccount-jwt` verifies on every subsequent request, carrying no role/scope claim.
- **`serviceaccount-assertion` provider**: The proof-of-possession AuthN provider that verifies a client assertion against the persistent `ServiceAccount` registry and gates `issueServiceAccountToken`.
- **`serviceaccount-jwt` provider**: The AuthN provider that verifies access tokens on ordinary GraphQL HTTP/WebSocket requests.
- **Controller credential signer**: The `gitstore-controller-manager`-side component holding an enrolled private key, responsible for signing assertions, exchanging them, and caching/renewing the resulting access token.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can obtain a working `gitstore-controller-manager` credential end-to-end (create `ServiceAccount` → enroll key → exchange assertion → authenticate a GraphQL request) with zero `static-admin` or `static-users` identity present anywhere in the deployment.
- **SC-002**: 100% of `issueServiceAccountToken` calls whose assertion does not match an enrolled, currently-active key for the targeted account are denied, with zero tokens issued for a mismatched or disabled/deleted account.
- **SC-003**: 100% of `serviceaccount-jwt`-authenticated principals carry an empty `Roles` field; authorization outcomes for two service accounts bound to two different `rbac-local` roles differ correctly for at least one role-differentiated action, with zero `rbac-local` source changes.
- **SC-004**: A running controller-manager configured with only a `ServiceAccount` signer (no `GITSTORE_CONTROLLER__API_TOKEN`) recovers and reaches readiness after a simulated outage exceeding its access token's lifetime, with zero administrator action taken during recovery.
- **SC-005**: A deployment that adds neither `serviceaccount-assertion` nor `serviceaccount-jwt` to `auth.authn.chain` shows zero observable behavior change versus its pre-spec state — same startup behavior, same default chain, same existing test suite results.
- **SC-006**: 100% of open WebSocket subscriptions for a disabled/deleted `ServiceAccount` are closed within one reconciliation of the disable/delete event, without waiting for the token's natural expiry.
- **SC-007**: Zero occurrences of a raw access token, client assertion, or private key value in any log line emitted by `serviceaccount-assertion`, `serviceaccount-jwt`, or the controller-manager's credential signer, verified by a grep-based CI check.

## Assumptions

- A service account's subject string is a **permanent, Git-visible audit identity**, not merely a log field. `Service.commitAndAdmitNamespace` passes `callerUsername` as the Git commit `AuthorName` for namespace manifests, and `CreateRepository`/`RenameRepository`/namespace admission persist it as `CreationActor`/`UpdateActor`. Once the controller authenticates as `serviceaccount:controllers:gitstore-controller-manager`, that string is written into Git history and datastore audit fields and cannot be rewritten later. Subject naming is therefore a one-way decision and MUST be settled before the first non-test commit is authored by a service account. (Verified 2026-08-30 against `gitstore-api/internal/graph/resolver/service.go` and `internal/namespace/admission.go`; no actor-format validation exists, so the `serviceaccount:<ns>:<name>` colon form is accepted as-is.)

- This spec adopts `docs/implementation/021-controller_service_account_auth.md`'s already-completed research and design decisions (§5 options comparison, §8 interfaces, §9 claim contracts, §14 phased plan) as authoritative and does not re-derive them; `research.md` records only what was newly verified against the current codebase (citation drift, call-site counts, the actual `bootstrap-token`/`gitctl` mechanics) and any scoping decisions this spec's own phasing required.
- Doc 021 §14's Phase 1 is this spec's User Story 1–3 (P1) scope; Phases 2–4 map to User Stories 5, 4, and 6 respectively (reordered by actual urgency to spec 060, not doc 021's phase numbering, since Phase 3's controller-side renewal is more urgent to production-usability than Phase 2's enrollment tooling, though either can be built first without blocking the other). Doc 021 §14 Phase 5 (flipping `auth.authn.chain`'s *default* to include both providers, and shipping `policy.yaml`'s `gitstore-controller-manager` role/binding as a documented default) is deferred to `tasks.md`'s final phase and is explicitly **not** required for this spec's own Success Criteria — the opt-in-only posture (FR-009) is what this spec ships; changing the *default* chain is a separate, later decision this spec deliberately does not make, mirroring how spec 060 already owns the human-provider default-chain question independently.
- Doc 021 §14 Phase 6 (an optional, future, in-cluster `oidc-jwt`-style provider trusting Kubernetes-issued ServiceAccount tokens) is explicitly out of scope for this spec, exactly as doc 021 itself scopes it — additive, disabled by default, revisited only once an actual in-cluster deployment need materializes.
- Multi-replica `gitstore-api` deployments require a shared assertion-`jti` replay store and a cross-replica revocation-broadcast mechanism before this feature is safely enabled across replicas (doc 021 §15's own flagged risk, re-confirmed unchanged). This spec targets the single-instance profile for its replay cache and WebSocket connection registry (both in-memory, per doc 021 §8c/§8d); the persistent `ServiceAccount` registry itself (FR-001) is multi-replica-safe from the start because it is datastore-backed, not in-memory. A follow-on spec is required before enabling this feature in a genuinely multi-replica `gitstore-api` deployment.
- `docs/implementation/021-controller_service_account_auth.md`'s own citations of `gitstore-api`/`gitstore-controller-manager` source line numbers were re-verified during this spec's writing (2026-08-29) and found substantially accurate in shape (the `AuthNProvider` interface, `GraphQLAuthenticator`'s `AroundOperations` wiring, `transport.Websocket`'s missing `InitFunc`, `buildProviderRegistry`'s chain-dispatch shape) with one material drift: doc 021 §2 describes a single `graphqlclient.New(cfg.Controller.ApiURI, cfg.Controller.ApiToken)` call site at `main.go:101`; the current codebase (`gitstore-controller-manager/cmd/controller/main.go`) constructs **three** separate `graphqlclient.Client` instances — one each in `registerNamespace`, `registerCategoryTaxonomy`, and `registerProductWatch` — each currently taking the same immutable token. User Story 4's `CredentialSource` design MUST be constructed once and shared across all three registration call sites (a single renewing credential source, not three independently-renewing ones), not merely substituted in at doc 021's originally-cited single call site — recorded in `research.md`.
- No existing GitHub issue tracks "controller-manager service-account authentication" specifically. `docs/implementation/021-controller_service_account_auth.md` itself is the tracking artifact prior to this spec; a tracking issue should be opened (or this spec linked to a new one) before `/speckit.plan`/`/speckit.tasks` work is treated as committed, matching the convention spec 058 already followed for its own untracked ADR-derived scope.
- This spec does not modify `docs/implementation/022-opa-data-authorization.md`'s scope. That document already extends this one (doc 021) with OPA-backed service-account role resolution and the `category.list`/`category.watch`/`product.list`/`product.read.unpublished` read-path enforcement doc 021 §10a reserves but does not itself enforce; this spec ships the reserved action strings in `policy.yaml`'s example role (User Story 3) but does not implement general GraphQL read-path gating.
- Following spec 059's precedent for `docs/implementation/020-pluggable_auth_architecture.md`, this spec adds a short addendum to that document's Phase 7 section (originally "OIDC JWT provider," which doc 021's own header already states this spec supersedes for the controller-identity use case) cross-referencing this spec, without altering Phase 7's `oidc-jwt` design for human/external-IdP use — `oidc-jwt` and `serviceaccount-jwt` remain two entirely distinct providers for two entirely distinct principal types.
